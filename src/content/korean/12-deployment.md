## 브라우저에 필요한 것만 공개하기

이 독서 목록은 정적 애플리케이션(static application)입니다. 호스트(host)는 HTML, CSS, JavaScript 파일을 보내고, 방문자의 브라우저가 사용자 입력과 localStorage를 처리합니다. 별도의 애플리케이션 서버나 데이터베이스는 필요하지 않습니다. 배포 과정을 확인할 수 있고 이전 배포본으로 되돌릴 수 있는 정적 호스팅 서비스를 고르세요.

배포 디렉터리에는 페이지와 스타일, 브라우저 모듈(module), 필요한 리소스(asset)를 담으세요. 저장소 메타데이터(metadata)나 인증 정보(credential), 개인 메모, 개발 전용 파일까지 실수로 올리지 않도록 살펴봅니다. 저장소에서 바로 배포하는 서비스라면 배포 디렉터리 설정을 확인하세요. 저장소 루트 전체를 공개해도 된다고 가정하면 안 됩니다.

배포 전에 테스트와 로컬 브라우저 점검을 마치고, 공개할 커밋을 기록하세요. 업로드 성공은 호스트가 파일을 받았다는 뜻입니다. 공개된 페이지를 열어 그 파일들이 실제로 함께 작동하는지는 다시 확인해야 합니다.

## 배포 경로에서 직접 테스트하기

호스팅 서비스에 따라 도메인 루트에 배포할 수도 있고, `/reading-list/` 같은 프로젝트 경로 접두사(prefix) 아래에 배포할 수도 있습니다. 루트 상대 경로(root-relative path)는 도메인 루트에서 시작합니다. 따라서 프로젝트 경로 아래에 배포하면 의도한 파일을 가리키지 않을 수 있습니다.

```html
<!-- 문서가 있는 디렉터리를 기준으로 하는 상대 경로 -->
<link rel="stylesheet" href="./styles.css">
<script type="module" src="./app.js"></script>
```

JavaScript 모듈 안의 가져오기 경로는 그 구문을 작성한 모듈의 URL을 기준으로 해석됩니다. 이 경로도 파일 이름의 대소문자까지 맞는지 확인하세요. 로컬 파일 시스템에서는 구분하지 않던 차이 때문에 호스트에서는 파일을 못 찾을 수 있습니다. `.mjs`를 썼다면 호스트가 이 파일을 JavaScript MIME 유형(MIME type)으로 보내는지도 확인합니다.

실제 공개 URL을 열어 개발자 도구의 Network 패널에서 실패한 요청을 살펴보세요. 그 주소에서 직접 새로고침도 해 봅니다. 프로젝트 디렉터리 주소 끝의 슬래시(trailing slash)를 호스트가 어떻게 처리하는지도 확인하세요. 디렉터리 URL을 파일 URL로 취급하면 상대 링크가 다르게 해석될 수 있습니다. `base` 요소를 넣으면 문서 안의 여러 URL에 영향을 주므로 경로 문제를 고치겠다고 쉽게 추가하지 마세요.

## 브라우저 설정은 공개 정보로 다루기

일반적인 브라우저 스크립트는 터미널의 환경 변수(environment variable)를 자동으로 읽을 수 없습니다. 빌드 도구(build tool)가 그 값을 결과물에 넣어 줄 수는 있습니다. 하지만 브라우저로 보내는 값은 방문자도 볼 수 있습니다. 변수 이름이 `SECRET`이어도 결과물에 들어간 뒤에는 비밀이 아닙니다.

이 앱에는 API 키가 필요하지 않습니다. 나중에 비공개 인증 정보를 쓰는 기능을 추가한다면 신뢰할 수 있는 서버 측 경계를 마련하거나 설계를 바꿔야 합니다. 키를 JavaScript나 localStorage에 넣는 방식으로 해결하려고 하지 마세요.

배포한 사이트와 로컬 서버는 출처(origin)가 다릅니다. 개발 중에 만든 목록이 온라인에 자동으로 나타나지 않는 이유입니다. 데이터가 사라졌다고 설명하지 말고 저장 영역이 다르다는 점을 알려 주세요. 호스트 이름이 다른 미리보기 배포도 저장소를 따로 씁니다. 반대로 출처가 같으면 경로 접두사가 달라도 localStorage를 공유합니다. 이름 공간(namespace)을 구분하는 키가 필요한 이유가 여기에 있습니다.

## 실제 사용 흐름과 접근성 확인하기

공개된 페이지에서 제목을 추가하고 읽음 상태를 바꾼 뒤, 새로고침해 저장된 상태를 확인하세요. 형식에 맞지 않는 제목과 마크업처럼 생긴 제목도 넣어 봅니다. 마크업처럼 생긴 제목은 글자 그대로 보여야 합니다. 키보드만으로 같은 과정을 반복하면서 포커스가 보이는지, 조작 요소의 이름을 이해할 수 있는지, 갱신 뒤에도 포커스가 자연스러운 위치에 있는지 살펴보세요.

화면을 좁히고 브라우저를 확대한 상태에서도 살펴보세요. 조작 요소가 잘리거나 가로 스크롤이 생기지는 않는지, 명암 대비 때문에 읽기 어렵지는 않은지 확인합니다. 상태 메시지가 색상으로만 뜻을 전달해서도 안 됩니다. 자동 접근성(accessibility) 검사로 일부 문제를 찾을 수는 있지만, 사용자가 상호작용을 이해하기 쉬운지까지 보장하지는 못합니다. 가능하면 보조 기술(assistive technology)로 페이지를 읽어 보고 실제로 확인한 내용을 기록하세요.

## 문제가 생기기 전에 되돌릴 방법 정하기

정상 동작을 확인한 배포본이나 커밋을 보관하고 호스트의 복원 절차를 미리 익혀 두세요. 새 버전이 로드되지 않아 이전 버전으로 되돌렸다면 공개 URL에서 다시 확인합니다. 브라우저가 요청하는 리소스도 살펴보세요. 캐시 때문에 복원된 버전의 전달이 늦어질 수 있어 한 번 새로고침한 화면만으로는 방문자가 받는 파일을 판단하기 어렵습니다.

코드를 이전 버전으로 돌리는 롤백(rollback)을 해도 localStorage는 되돌아가지 않습니다. 나중에 데이터 형식을 마이그레이션(migration)하면 이전 코드로는 새 데이터를 읽지 못할 수 있습니다. 마이그레이션은 별도 작업으로 나눠 호환성을 테스트하세요. 저장 형식을 바꾸기 전에는 복구하거나 내보낼 수 있는 기능도 제공해야 합니다. 이 강좌에서 키에 버전을 넣은 것은 저장 형식에 대한 결정을 드러내기 위해서입니다. 버전이 있다고 마이그레이션까지 자동으로 처리되지는 않습니다.
