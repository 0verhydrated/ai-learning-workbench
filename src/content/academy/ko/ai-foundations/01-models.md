## 모델, 앱, 제공업체는 어떻게 다를까요?

<strong>모델</strong>은 입력을 받아 예측하거나 출력을 만드는 계산 시스템입니다. 학습 과정에서 가중치라는 수치 매개변수를 조정합니다. <strong>앱</strong>은 이 모델을 이용하는 제품으로, 채팅 화면부터 문서 업로드, 검색, 대화 저장, 권한 관리, 도구까지 포함합니다. <strong>제공업체</strong>는 모델을 운영하거나 모델에 접근할 수 있게 해 주는 업체입니다. 한 업체가 여러 모델을 제공하기도 하고, 한 앱이 요청에 따라 서로 다른 업체의 모델을 쓰기도 합니다.

같은 이름의 모델을 쓰더라도 앱에 따라 답변은 달라질 수 있습니다. 최신 설명서를 검색해 모델에 전달하는 앱이 있는가 하면 질문만 보내는 앱도 있습니다. 코드를 격리된 환경에서 실행할 수도, 코드처럼 생긴 텍스트만 작성할 수도 있습니다. 그래서 답변을 볼 때는 어떤 모델을 썼는지, 무슨 근거를 전달했는지, 도구를 실제로 실행했는지를 따로 확인해야 합니다. 말이 유창하다는 이유만으로 이 중 어느 것도 확인됐다고 볼 수는 없습니다.

<strong>학습</strong>에서는 데이터와 학습 목표에 따라 매개변수를 바꿉니다. 사전 학습으로 폭넓은 능력을 익힌 뒤, 미세 조정으로 특정 데이터를 추가 학습할 수 있습니다. <strong>추론</strong>은 이렇게 학습한 모델로 새 입력을 처리하는 과정입니다. Hugging Face는 모델의 구조를 뜻하는 아키텍처와 그 구조에 불러올 특정 가중치인 체크포인트를 구분합니다.[1] 대화 도중 문체 안내서를 건네면 보통은 그 내용을 추가 문맥으로 활용해 추론합니다. 이때 바로 학습이 일어나는 것은 아닙니다. 제출한 데이터를 서비스가 나중에 학습에 쓰는지는 별도의 정책을 확인해야 합니다.

## 작업에 필요한 능력부터 살펴보세요

추론 특화 모델은 어려운 문제를 풀기 위해 답변 전에 계산을 더 수행할 수 있습니다. 여러 단계를 거치는 버그 분석에 도움이 될 수 있지만, 그만큼 비용이나 대기 시간이 늘기도 합니다. 조절할 수 있는 설정도 모델마다 다릅니다.[2] 오래 생각했다고 반드시 맞는 답이 나오는 것은 아닙니다. 설명의 길이로 판단하지 말고 수정한 코드를 테스트하거나 계산 결과를 검증하세요.

멀티모달 모델은 텍스트와 이미지처럼 둘 이상의 형식을 처리합니다. 다만 무엇을 입력받을 수 있는지와 무엇을 출력할 수 있는지는 따로 봐야 합니다. 스크린샷을 읽는 모델이라고 해서 이미지를 만들거나 음성을 받아쓸 수 있는 것은 아닙니다. 화면 오류를 조사한다면 스크린샷으로 버튼이 겹친 모습을 볼 수 있습니다. 접근성 텍스트와 소스 코드도 함께 주면 화면만으로 읽기 어려운 정확한 문구와 버튼의 동작을 확인하는 데 도움이 됩니다.

로컬로 배포하면 직접 관리하는 하드웨어에서 추론을 실행합니다. 오프라인으로 작업하거나 데이터가 이동하는 경로를 통제하기에 유리할 수 있습니다. 대신 메모리, 설치, 업데이트, 보안, 성능을 직접 챙겨야 합니다. 클라우드는 이 중 상당 부분을 업체에 맡기고 노트북에서 실행하기 어려운 기능도 쓸 수 있지만, 네트워크와 업체의 데이터 처리 정책에 의존합니다. 로컬에서 실행한다고 개인정보가 저절로 보호되지는 않습니다. 플러그인, 원격 측정, 외부 도구도 점검하세요. 가중치가 공개된 모델 역시 사용 조건에 제한이 있을 수 있습니다.

## 선택 사례: 가상의 고객 지원 도우미

고객 지원 도우미가 문의를 분류하고, 스크린샷의 오류를 설명하고, 복잡한 계정 절차에서 생긴 문제까지 해결해야 한다고 해 봅시다. 작업마다 필요한 능력이 다르니 모두 가장 비싼 설정으로 처리할 필요는 없습니다.

| 작업 | 먼저 시험할 후보 | 합격 기준 |
| --- | --- | --- |
| 짧은 문의 분류 | 저비용 텍스트 모델 | 분류와 출력 형식이 모두 정확함 |
| 스크린샷 해석 | 이미지 입력 지원 모델 | 실제 오류를 읽고 없는 문구를 만들지 않음 |
| 절차 오류 진단 | 추론 특화 모델 | 설명이 로그 및 재현 테스트와 일치함 |

먼저 민감 정보를 뺀 작은 평가 자료를 만드세요. 명확한 사례만 모으지 말고 애매한 표현, 한국어 문의, 정보가 부족한 질문, 오해하기 쉬운 스크린샷도 넣습니다. 정답은 프롬프트에 넣지 않고 따로 보관하세요. 후보마다 같은 입력과 도구를 제공한 뒤 정확성, 근거 없는 주장, 응답 시간, 비용을 기록합니다. 한 번 잘 나왔다고 고르지 말고 반복해서 측정하세요. 공식 최적화 안내에서도 실제 입력을 대표하는 평가 자료를 준비하고 기준 성능을 측정하는 일부터 시작하라고 권합니다.[3]

문의 분류에서는 설명이 훌륭해도 필수 필드가 빠지면 결과를 사용할 수 없습니다. 이런 작업에는 간단한 모델에 확실한 검증 절차를 붙이는 편이 나을 수 있습니다. 정해진 규칙으로 분류할 수 있다면 모델 없이 조회 표로 처리하는 방법도 검토하세요.

## 실습: 선택 근거 남기기

오프라인 워크숍에서 가상의 문의를 분류하려고 합니다. 어떤 도우미를 쓸지 고르고 배포 방식, 필요한 입력 형식, 합격 여부를 판단할 테스트 하나, 실패했을 때의 처리 방식을 네 줄로 적어 보세요. 나중에 스크린샷 문제 해결이 추가되고 승인된 클라우드도 쓸 수 있게 된다면 선택이 어떻게 달라질지도 설명하세요.

<details>
<summary>답안 예시</summary>

로컬에서 실행할 수 있는 텍스트 모델을 먼저 고르고, 라이선스와 하드웨어 요구 사항을 확인합니다. 정답이 있는 문의와 잘못된 입력을 넣어 평가하세요. 허용하지 않은 분류 값은 거부하고, 판단이 불확실한 문의는 추측해서 처리하지 않고 사람에게 넘깁니다. 스크린샷을 다루게 되면 이미지 입력을 지원하는 로컬 모델이나 승인된 클라우드 후보를 다시 평가해야 합니다. 기존 텍스트 모델이 이미지도 볼 수 있다고 가정하면 안 됩니다. 개인정보 규칙을 재확인하고 실제 작업 결과를 비교한 뒤 전환하세요. 측정하기 전에는 어느 모델이 맞는 선택인지 단정할 수 없습니다.
