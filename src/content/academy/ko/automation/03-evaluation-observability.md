## 코드가 맞는지와 답변이 맞는지는 따로 확인합니다

<strong>단위 테스트</strong>는 코드의 좁은 동작 범위를 확인합니다. 파서가 날짜가 빠진 입력을 거부하는지 검사하는 식입니다. <strong>평가</strong>, 즉 eval에서는 여러 사례를 통해 모델을 활용한 동작이 작업 기준을 얼마나 충족하는지 측정합니다. 영어·한국어 요약에 단서 표현이 남아 있는지, 각 주장이 올바른 출처와 연결되는지 등을 살핍니다. 파서 테스트를 통과해도 요약이 사실과 맞는지는 따로 확인해야 합니다. 그럴듯한 요약을 만들었다고 재시도 처리기까지 올바르게 작동하는 것도 아닙니다.

OpenAI 평가 가이드는 작업을 정의하고 테스트 입력으로 실행한 뒤 결과를 분석하는 과정을 설명합니다 [1]. 특정 호스팅 제품을 쓰지 않아도 이 방법을 적용할 수 있습니다. 이 수업에서는 Evals API에 연결하지 않고 로컬 평가기를 사용합니다. 호스팅 도구를 선택한다면 해당 제품이 현재 제공되는지부터 확인하세요.

## 비교에 사용할 데이터셋 준비하기

<strong>정답 데이터셋</strong>에는 대표적인 입력과 검토를 마친 기대 답안 또는 평가 기준을 짝지어 담습니다. 뉴스라면 출처 발췌문, 발행일, 관련 주장, 허용되는 번역을 보존하세요. 다루기 쉬운 영어 발표문만 모아서는 부족합니다. 평범한 기사뿐 아니라 날짜가 충돌하거나 근거가 부족한 사례, 프롬프트 인젝션 문구, “예정” 같은 한국어 단서도 넣어야 합니다.

프롬프트를 반복해서 다듬을 개발용 집합과, 튜닝에 계속 사용하지 않을 별도의 홀드아웃 집합으로 나누세요. 데이터셋, 프롬프트, 모델 식별자, 설정은 함께 버전 관리합니다. 후보 버전과 기준 버전을 같은 사례로 비교하고, 실행마다 결과가 달라지는 정도가 중요하다면 반복 실행해 표본을 모으세요. 평균 점수에 더해 유형별 실패와 불확실성도 보고합니다. 작고 정제된 집합은 이전에 되던 것이 안 되는 회귀를 찾는 데 유용하지만, 전반적인 신뢰성을 증명하지는 못합니다.

## 오프라인에서 평가기 동작 확인하기

다음 프로그램은 표준 라이브러리와 <strong>직접 작성한 가상의 픽스처</strong>만 사용합니다. 네트워크에 요청하거나 모델을 실행하지 않습니다. 후보 답변에는 일부러 오류를 넣었습니다. 한 사례에서는 단서를 제거하고 다른 사례에서는 날짜를 지어냈으므로, 평가기가 두 실패를 찾아내야 합니다. 여기서 나온 결과는 검사 장치가 작동하는지 보여 줄 뿐, 모델 성능을 측정한 값은 아닙니다.

```python
fixtures = [
    {"id": "a", "gold": {"date": "2026-11-01", "status": "planned"},
     "candidate": {"date": "2026-11-01", "status": "launched"}},
    {"id": "b", "gold": {"date": "2026-11-02", "status": "launched"},
     "candidate": {"date": "2026-11-02", "status": "launched"}},
    {"id": "c", "gold": {"date": None, "status": "unknown"},
     "candidate": {"date": "2026-11-03", "status": "unknown"}},
]
results = []
for row in fixtures:
    actual, expected = row["candidate"], row["gold"]
    passed = set(actual) == set(expected) and actual == expected
    results.append((row["id"], passed))
assert results == [("a", False), ("b", True), ("c", False)]
print({"passed": sum(ok for _, ok in results), "total": len(results)})
```

결정적 검사는 스키마, 필수 필드, 허용된 식별자, 정확히 추출해야 하는 사실을 확인하는 데 적합합니다. 다만 서술 전체에 근거가 있는지까지 판단하지는 못합니다. 주장과 출처를 연결해 검토하고, 내용이 빠지지 않았는지, 의미와 불확실성이 보존됐는지도 평가하세요. 모델을 심사자로 쓴다면 사람이 붙인 라벨과 비교해 보정해야 합니다. 심사자는 긴 답변이나 자신의 문체를 선호하고, 제시 순서에 영향을 받을 수 있습니다. 어떤 후보의 답변인지 숨기고 순서를 무작위로 섞은 뒤, 사람과 판단이 다른 사례를 검토하세요. 신뢰할 수 없는 후보 답변이 채점 지침을 정하도록 두어서는 안 됩니다.

## 실제 실행을 관측하기

<strong>관측 가능성</strong>은 시스템이 내보내는 신호로 내부 동작을 이해하는 능력입니다. OpenTelemetry는 로그, 메트릭, 트레이스를 구분하며, 트레이스는 작업 단위를 나타내는 스팬으로 구성됩니다 [2]. 뉴스 파이프라인에는 실행 전체의 루트 스팬과 수집, 검증, 요약, 출력 검사, 승인, 발행 단계의 하위 스팬을 둡니다.

실행 ID와 단계, 소요 시간, 재시도 횟수, 도구 오류 분류, 프롬프트 버전, 모델 식별자를 기록하세요. 지연 시간 분포와 큐 대기 시간, 검증 실패와 전달 누락도 추적합니다. 토큰 사용량이 제공되면 기록하되, 사용량을 모를 때는 0으로 적지 말고 알 수 없다고 표시하세요. 비용을 계산했다면 어떤 버전의 가격표로 추정했는지 밝힙니다. 도구의 성공 응답을 받았어도 사용자에게 필요한 결과가 도착했는지는 따로 확인해야 합니다.

관측 데이터에는 인증 정보, 비공개 원문, 전체 프롬프트, 민감한 쿼리 문자열을 기본적으로 남기지 마세요. 허용 목록에 있는 속성만 남기고 접근 제어와 보존 기한, 검토를 거친 마스킹을 적용합니다. 상관관계 ID로 운영 이벤트를 연결하되, 이 ID를 통해 개인정보를 모으는 별도 저장소를 만들지 않도록 주의하세요.

## 연습: 평균 점수가 올라도 배포할 수 없는 경우

<strong>연습:</strong> 후보 버전이 단위 테스트를 통과했고 심사자의 평균 점수도 올랐습니다. 그런데 한국어 요약에는 출시 예정 제품이 이미 출시된 것으로 적혀 있습니다. 이 버전을 배포해도 될까요?

배포하면 안 됩니다. 검토를 마친 단서 표현 사례와 한국어 사실성 통과 조건을 추가하고, 심사자의 판단이 어긋난 사례를 살펴보세요. 튜닝에 쓰지 않은 홀드아웃에서도 비교해야 합니다. 평균 점수가 올라도 한국어 요약에서 출시 여부를 잘못 옮기는 회귀는 가려질 수 있습니다. 비공개 원문을 로그에 남기지 않으면서 문제가 생긴 단계를 추적하세요. 테스트가 통과하고 문장이 유창하며 지연 시간이 정상이어도, 요약의 의미가 근거와 맞는지는 별도로 검증해야 합니다.
