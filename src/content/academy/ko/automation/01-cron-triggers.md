## 예약을 저장한 뒤에도 확인할 일이 있습니다

<strong>트리거</strong>는 작업을 요청합니다. 언제 요청할지는 <strong>스케줄러</strong>가 정하고, 실제 작업은 <strong>워커</strong>가 맡습니다. 일정을 저장했더라도 워커가 시작됐는지, 유효한 자료를 가져왔는지, 결과까지 전달했는지는 아직 모릅니다. 이 과정을 확인할 수 있도록 예약됨, 시작됨, 완료됨, 전달됨을 각각 기록하세요.

노트북에서 실행하는 주간 뉴스 도우미라면 일요일로 예약해 두어도 노트북이 잠들어 있을 때는 작업할 수 없습니다. 예약과 함께 실행 환경도 준비해야 합니다. Hermes 문서에 따르면 예약 작업은 새로운 에이전트 세션에서 실행됩니다 [1]. 매번 새로 시작한다는 전제로 저장소 경로, 출처 정책, 출력 형식, 마감 시각, 영속 체크포인트 위치를 전달하세요. 어제 나눈 대화가 그대로 남아 있으리라 기대해서는 안 됩니다.

## 다섯 필드를 순서대로 읽기

일반적인 5필드 cron 표현식은 아래 순서로 읽습니다 [2].

```text
분     시   일(날짜)     월    요일
0      8    *            *     0
```

`*`는 허용되는 모든 값을 의미하며, 여기서 `0`은 일요일입니다. 따라서 `0 8 * * 0`은 <strong>스케줄러가 사용하는 시간대에서</strong> 일요일 08:00을 뜻합니다. 표현식 안에는 시간대 정보가 없습니다. UTC 스케줄러에 붙여 넣고 한국 시각으로 해석되기를 기대하면 안 됩니다.

요구 사항이 `Asia/Seoul` 기준 일요일 08:00이라면, UTC로 동작하는 스케줄러에서는 `0 23 * * 6`을 사용합니다. UTC 토요일 23:00에 해당하므로 시간뿐 아니라 날짜와 요일이 바뀌는지도 확인해야 합니다. 다음 코드는 파이썬 표준 라이브러리만 사용하며 실제 예약을 만들지 않습니다.

```python
from datetime import datetime, timezone
from zoneinfo import ZoneInfo

local = datetime(2026, 11, 8, 8, 0, tzinfo=ZoneInfo("Asia/Seoul"))
utc = local.astimezone(timezone.utc)
assert local.strftime("%A") == "Sunday"
assert utc.isoformat() == "2026-11-07T23:00:00+00:00"
assert utc.strftime("%A") == "Saturday"
print(local.isoformat(), "=>", utc.isoformat())
```

서머타임을 쓰는 지역에서는 UTC 시각을 고정해 두면 현지 실행 시각이 계절에 따라 달라질 수 있습니다. 스케줄러가 지원한다면 지역 이름으로 시간대를 지정하고, 시계가 바뀌는 시점 전후의 실행 예정 시각을 확인하세요. 일요일을 나타내는 번호나 날짜와 요일을 함께 지정했을 때의 해석도 cron 구현마다 다릅니다. 한 가지 문법을 모든 곳에 적용하지 말고 사용하는 스케줄러의 규칙을 확인하세요.

## 일정과 이벤트 중 선택하기

<strong>폴링</strong>은 변화가 있는지 반복해서 확인하는 방식입니다. <strong>웹훅</strong>은 이벤트를 보내는 쪽에서 변화를 감지해 알려 줍니다. 매주 요약을 발행할 때는 일정에 맞춰 실행하고, 풀 리퀘스트 리뷰에 반응할 때는 이벤트를 받는 편이 어울립니다. 다만 웹훅도 정확히 한 번만 전달된다고 보장할 수는 없습니다. 서명을 검증하고 재전송 공격을 막으며 중복 이벤트도 처리해야 합니다.

GitHub Actions의 예약 워크플로는 기본 브랜치에서 실행되며 문서에는 지연 가능성도 명시되어 있습니다 [2]. 호스팅된 워크플로는 노트북의 전원 상태에 의존하지 않지만, 별도의 로컬 Hermes 게이트웨이까지 클라우드에서 실행해 주지는 않습니다. 각 워커가 실제로 어디에서 실행되는지 확인하세요.

## 활성화 전에 실행 조건 정하기

작업을 켜기 전에 적용 시간대와 다음 세 번의 예정 시각을 적으세요. 중복 실행 정책, 최대 실행 시간, 놓친 일정의 처리 방식, 성공 결과를 전달할 위치도 정합니다. 지난주 작업을 놓쳤다면 건너뛸지 한 번 보충할지 미리 결정해 두세요. 수개월치 발행 작업이 한꺼번에 실행되는 일은 막아야 합니다.

Hermes의 예약 옵션을 쓰기 전에는 설치된 명령이나 도구 스키마를 최신 문서와 비교하세요. 문서가 설명하는 버전과 설치 버전이 다를 수 있습니다. 저장된 다음 실행 시각과 활성화 상태를 확인하고, 명시적으로 허용된 드라이런만 수행합니다. 이 수업에서는 실제 예약을 만들지 않습니다. 인증 정보는 실행 환경의 비밀 저장소에 두세요. cron 문자열이나 프롬프트, 커밋 파일, 알림 메시지에 넣어서는 안 됩니다.

## 연습: 시간대를 바꾸고 확인할 것

cron이 표현식을 받아들였다고 뉴스레터가 도착하는 것은 아닙니다. 설정부터 전달까지 단계마다 실제로 무엇이 끝났는지 확인할 근거가 필요합니다. 마지막에는 지정한 전달 위치를 다시 열어 결과를 확인하세요.

<strong>연습:</strong> 편집자는 한국 시각 일요일 08:00 실행을 요청했는데, UTC 워커에는 `0 8 * * 0`이 설정돼 있습니다. 어디를 고쳐야 할까요? 수정한 뒤에는 무엇을 더 확인해야 할까요?
