## 실패한 상황 보존하기

도우미에게 계속 "다시 해 봐"라고 요청하면 이해하지 못한 구현을 또 다른 이해하지 못한 구현으로 바꾸게 될 수 있습니다. 원래 증상을 놓치면서 다른 버그를 추가할 수도 있습니다. 먼저 실패를 재현하는 가장 짧은 순서를 기록하고 현재 변경 내역(diff)을 살펴보세요.

독서 목록에 책이 추가되는 듯하다가 곧바로 사라진다고 가정해 봅시다. URL, 브라우저, 재현 단계, 화면에서 보이는 동작, 콘솔(console) 메시지를 기록하세요. 페이지 전체가 다시 로드되나요? 직접 새로고침한 뒤에만 제목이 사라지나요? 이 관찰 결과들은 서로 다른 부분을 가리킵니다. 제출할 때 페이지가 다시 로드된다면 폼(form)의 기본 페이지 이동을 막지 못했을 가능성이 있습니다. 직접 새로고침했을 때 사라진다면 데이터를 저장해 유지하는 영속성(persistence) 기능이 없거나 실패했을 가능성이 있습니다.

저장된 데이터로 실험하기 전에 보관하고 싶은 목록을 복사하세요. 가능하다면 별도의 테스트용 출처(origin)나 임시 브라우저 프로필을 사용하세요. 디버깅(debugging)을 한다고 근거나 사용자의 실제 독서 목록을 함부로 없애서는 안 됩니다.

## 추측하지 말고 이벤트 따라가기

개발자 도구를 열고 Console과 Network 패널을 살펴보세요. `app.js`가 정상적으로 로드되었는지 확인하세요. 스크립트 누락, 문법 오류, 잘못된 선택자(selector) 때문에 이벤트 리스너(event listener)가 아예 등록되지 못할 수 있습니다. 관련 없는 곳에 `preventDefault()` 호출을 하나 더 넣어도 이 상황은 해결되지 않습니다.

잠시 관찰용 코드를 넣으면 도움이 될 수 있습니다.

```js
form.addEventListener('submit', event => {
  console.log('submit reached', { prevented: event.defaultPrevented });
  event.preventDefault();
  console.log('navigation prevented', event.defaultPrevented);
  // Existing validation and state update follow here.
});
```

중복 핸들러(handler)를 만들지 말고 기존 리스너 안에 관찰용 코드를 넣으세요. 이벤트 메타데이터(metadata)만으로 충분하다면 사적인 책 제목을 로그에 남기지 마세요. 진단이 끝나면 임시 로그를 지우거나, 유용한 검사를 테스트로 옮기세요.

로그를 더 남기는 것보다 중단점(breakpoint)이 나을 때가 많습니다. 핸들러 안에서 실행을 멈추고, 입력값과 책 배열을 살펴본 뒤, 한 단계씩 실행하세요. 화면이 왜 갱신되지 않았는지 묻기 전에 상태가 바뀌는지 확인하세요.

## 반증 가능한 가설 하나 세우기

가설은 관찰 결과를 예측할 수 있어야 합니다. "선택자가 잘못됐다"는 가설은 `document.querySelector('#book-form')`이 `null`을 반환할 것이라고 예측합니다. "다른 출처의 저장소를 사용하고 있다"는 가설은 호스트 이름이나 포트가 바뀌면 저장된 값이 다를 것이라고 예측합니다. 이런 예측이 있으면 애플리케이션을 다시 작성하지 않고도 설명이 틀렸는지 판단할 수 있습니다.

도우미에게 근거를 바탕으로 추론하도록 요청하세요.

```text
아직 파일은 바꾸지 마. 폼에서 Enter를 누르면 페이지가 다시 로드돼.
Network를 보니 app.js 요청이 404를 반환했어. HTML은 ./scripts/app.js를
요청하지만, 파일 트리에서는 app.js가 index.html 옆에 있어.
가능성이 높은 원인과 이를 확인할 수 있는 최소한의 검사를 설명해 줘.
관찰된 사실과 가정을 구분해 줘.
```

필요한 수정은 새 폼 라이브러리를 추가하는 것이 아니라 스크립트 경로를 고치는 것일 가능성이 높습니다. 경로를 바꾼 뒤 브라우저가 수정된 URL로 요청하는지, 핸들러가 실행되는지 확인하세요. 그럴듯한 설명도 원래 재현 절차에서 더 이상 실패하지 않는 것을 확인하기 전까지는 잠정적인 설명입니다.

## 수정 결과와 인접한 동작 검증하기

실패했던 순서를 똑같이 다시 실행하세요. 그런 다음 마우스로 제출하기, 키보드로 제출하기, 공백 입력하기, 책 두 권 연속 추가하기처럼 인접한 경우도 확인하세요. 수정한 코드에 순수 로직(pure logic)이 있다면 그 로직에 대한 회귀 테스트(regression test)를 추가하세요. 브라우저의 로드 실패는 여전히 브라우저나 HTTP 수준에서 확인해야 합니다. 단위 테스트(unit test)로는 HTML 경로가 올바른지 증명할 수 없습니다.

최종 변경 내역을 살펴보세요. 추측으로 넣었다가 필요하지 않았던 수정은 제거하세요. 증상, 원인, 변경 사항, 실제로 수행한 검사를 짧게 기록하세요. 문제를 재현하지 못했다면 코드만 살펴보고 고쳤다고 주장하지 말고, 재현하지 못했다고 밝히세요.
