## 실패 뒤에도 안전하게 복구하려면

<strong>신뢰할 수 있는 워크플로</strong>는 예상 가능한 실패를 겪어도 허용된 결과에 도달합니다. 복구할 수 없다면 운영자가 상황을 파악하고 조치할 수 있는 상태에서 멈춰야 합니다. 성공할 때까지 무한히 재시도하면 같은 기사를 여러 번 발행할 수 있습니다. HTTP 요청이 결국 성공했더라도 중복 발행은 별도로 막아야 합니다.

실패 뒤에 한 번 더 시도하는 것을 <strong>재시도</strong>라고 합니다. 같은 논리적 작업을 반복해도 의도한 효과가 추가로 생기지 않는 성질은 <strong>멱등성</strong>입니다. 여기에 반복 입력을 알아보는 <strong>중복 제거</strong>, 완료한 단계를 보존해 이어서 작업하게 하는 <strong>체크포인트</strong>를 함께 사용합니다. 서로 보완하는 장치들이지만, 어느 하나만으로 독립적인 여러 시스템에 걸쳐 정확히 한 번 실행된다고 보장할 수는 없습니다 [1][2].

## 재시도 횟수와 시간을 제한하기

일시적인 연결 실패나 일부 서버 오류, 요청 제한은 서비스 계약이 허용한다면 재시도할 수 있습니다. 잘못된 입력, 권한 부족, 안전 검증 거부가 원인이라면 같은 요청을 무작정 반복하지 마세요. 타임아웃도 주의해서 해석해야 합니다. 서버가 이미 쓰기를 마쳤는데 응답만 도착하지 않았을 수 있으므로, 실패가 확정됐다고 보면 안 됩니다.

연결 및 요청 타임아웃, 최대 시도 횟수, 전체 마감 시간, 비용 상한을 함께 정하세요. 지수 백오프는 실패할수록 대기 시간을 늘리는 방식입니다. 여기에 지터를 적용하면 클라이언트들이 동시에 재시도하지 않도록 대기 시간을 분산할 수 있습니다 [1]. 예를 들어 총 네 번 시도한다면, 재시도 번호가 0부터 2일 때 0초와 `min(8, 2 ** retry_index)`초 사이에서 대기 시간을 무작위로 뽑을 수 있습니다. 각 상한은 1초, 2초, 4초입니다. 다만 이 값은 대기 시간만 제한합니다. 통신에 걸리는 시간까지 제한하지는 않으므로 각 요청의 타임아웃과 전체 작업의 마감 시간도 필요합니다.

유효한 `Retry-After`를 받았다면 남은 예산 안에서 따르세요. 기다리다 마감 시간을 넘기게 된다면 작업을 연기하거나 실패로 처리합니다. 값을 무시하고 즉시 재시도해서는 안 됩니다. 재시도를 책임지는 계층도 하나로 정하세요. SDK, 워커, 큐가 저마다 재시도하면 트래픽과 비용이 곱절로 늘어날 수 있습니다. 기록에는 “실패”라는 말만 남기지 말고 몇 번 시도했고 왜 최종 중단했는지도 적으세요.

## 로컬 중복 제거를 원자적으로 만들기

표식 파일이 없으면 만드는 방식으로는 동시 실행을 막기 어렵습니다. 두 워커가 모두 파일이 없다고 확인한 뒤 만들 수 있기 때문입니다. 데이터베이스의 고유성 제약을 사용하면 하나의 워커만 작업을 선점하도록 원자적으로 처리할 수 있습니다. 아래 오프라인 예제는 임시 디스크에 SQLite 데이터베이스를 만듭니다. 로컬 상태 관리만 보여 주며 원격 발행은 하지 않습니다.

```python
import sqlite3
from tempfile import TemporaryDirectory
from pathlib import Path

with TemporaryDirectory() as folder:
    path = Path(folder) / "jobs.sqlite"
    db = sqlite3.connect(path)
    db.execute("CREATE TABLE jobs (id TEXT PRIMARY KEY, state TEXT NOT NULL)")
    key = "weekly:2026-11-08:en-ko:v1"
    def claim():
        with db:
            return db.execute(
                "INSERT OR IGNORE INTO jobs VALUES (?, 'pending')", (key,)
            ).rowcount == 1
    assert claim() is True
    assert claim() is False
    with db:
        db.execute("UPDATE jobs SET state='drafted' WHERE id=?", (key,))
    db.close()
    db = sqlite3.connect(path)
    assert db.execute("SELECT state FROM jobs").fetchone() == ("drafted",)
    print("one claim; checkpoint survives reconnect")
    db.close()
```

실제 운영에서는 데이터베이스를 영속 경로에 두고 백업과 상태 머신도 갖춰야 합니다. 대기, 초안 작성, 승인, 발행 중, 발행 완료, 차단 상태를 구분하세요. 산출물 해시, 출처 식별자, 발행 대상 ID, 오류도 상태와 함께 저장합니다. 멱등성 키 하나는 하나의 작업 의도를 가리켜야 합니다. 내용이 바뀌었다면 예전 키를 그대로 재사용하지 말고 개정됐음을 명시하세요.

## 원격 쓰기와 로컬 기록 사이의 틈

원격 발행 후 로컬에 완료 상태를 저장하기 전에 프로세스가 죽으면 결과가 불확실해집니다. 로컬 표식만으로는 이 틈을 해결할 수 없습니다. 대상 서비스가 지원하는 멱등성 키를 사용하고 안정적인 식별자로 결과를 다시 읽어 확인하세요 [2]. 둘 다 지원되지 않는다면 재발행 전에 대조 확인이나 사람의 검토가 필요합니다.

어느 워커가 작업을 맡고 있는지도 관리해야 합니다. 트랜잭션으로 선점하거나, 필요에 따라 만료와 펜싱을 갖춘 임대 방식을 사용하세요. 펜싱은 이전 소유자가 더 이상 쓰지 못하게 막습니다. 오래 대기했다는 이유만으로 작업을 초기화하면 첫 워커가 아직 발행을 진행할 수 있습니다. 체크포인트에서 재개할 때도 산출물이 검증된 상태인지 살펴야 합니다. 초안이 바뀌었다면 다시 검증하세요.
