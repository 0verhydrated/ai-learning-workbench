## 구조를 바꾸기 전에 문제부터 정의하기

리팩터링(refactoring)은 외부에서 보이는 의도한 동작은 그대로 두고 내부 구조를 바꾸는 일입니다. 다음 기능을 만들기 쉬워질 수는 있지만, 도우미에게 "전부 정리해 줘"라고만 해서는 무엇을 고칠지 분명하지 않습니다. 같은 검증을 여러 번 하는지, 처리 함수(handler) 하나가 너무 많은 일을 하는지, 저장 로직을 브라우저 없이 테스트할 수 없는지부터 살펴보세요.

지금 독서 목록은 폼 입력, 데이터 변환, 화면 표시, 저장을 다루지만, 여전히 파일 하나로 읽을 만한 크기일 수 있습니다. 한 부분을 고칠 때 무관한 코드까지 손대지 않게 하거나 독립적으로 테스트할 수 있게 된다면 분리할 만합니다. 파일 수가 늘었다는 사실만으로 구조가 나아지지는 않습니다.

처음에는 저장 기능부터 나눠 볼 만합니다. JSON 파싱과 검증을 모듈(module)로 옮기면 Node에서 직접 테스트할 수 있습니다. localStorage를 가져오고 오류를 화면에 알리는 부분은 브라우저 어댑터(adapter)에 남겨 두세요.

## 유지하려는 동작 확인하기

고치기 전에 기존 테스트부터 실행하고, 실패하는 항목을 기록하세요. 브라우저에서도 책 추가, 읽음 상태 전환, 새로고침, 키보드 조작을 차례로 확인합니다. 동작을 설명한 문서가 없다면 현재 코드가 하는 일을 테스트로 남기세요. 이를 특성화 테스트(characterization test)라고 합니다. 기록한 뒤에는 그 동작을 앞으로도 유지할지 판단해야 합니다.

특성화 테스트에 알려진 버그가 담겼다고 그 버그까지 유지할 필요는 없습니다. 수정할 기대 결과를 따로 적고 동작 변경으로 다루세요. 코드를 옮기는 일과 나눠 두면 검토할 때 의도한 수정과 우연히 생긴 차이를 구분할 수 있습니다.

Git으로 작업 시작 상태를 확인하세요.

```sh
git status --short
git diff
node --test books.test.mjs
```

이번 작업과 관계없는 로컬 변경은 덮어쓰지 마세요. 함께 사용하는 코드를 옮기기 전에는 확인된 상태를 커밋(commit)하거나 작업한 사람과 조율하세요. 작업 트리(working tree)가 깨끗하면 구분하기 편합니다. 변경이 남아 있다면 어느 것이 이번 작업에 속하는지 먼저 파악하세요.

## 한 번에 하나의 책임만 옮기기

프롬프트(prompt)에는 옮길 부분과 바꾸지 않을 부분을 함께 적으세요.

```text
parseBooks를 storage.mjs로 분리하세요. 허용하는 형식, 오류 동작,
저장소 키는 바꾸지 마세요. 가져오기 구문과 테스트를 갱신하세요.
화면 표시를 바꾸거나 DOM ID의 이름을 변경하거나 의존성을 추가하거나
데이터 마이그레이션을 도입하지 마세요. 변경분과 실제 테스트 결과를 보여 주세요.
동작을 바꿔야 한다면 작업을 멈추고, 진행하기 전에 이유를 설명하세요.
```

함수를 옮기고 가져오기 구문을 수정한 뒤 해당 부분의 테스트를 실행하세요. 이어서 실행할 수 있는 전체 테스트를 돌리고, 모듈 경로가 달라진 브라우저 동작도 확인합니다. 함수 내용이 그대로여도 가져오기 경로에 오타가 있으면 페이지가 작동하지 않을 수 있습니다.

분리한 코드를 확인한 뒤에는 제출 처리에서 입력 정규화, 상태 변환, 화면 표시, 저장 결과 알림을 나눌 수 있습니다. 실행 순서를 유지하고 저장 결과가 알림 단계까지 전달되도록 하세요. 보조 함수가 그 정보를 빠뜨리면 저장에 실패해도 성공 메시지가 나올 수 있습니다.

## 정리하면서 동작까지 바꾸지는 않았는지 살피기

들여쓰기나 파일 배치만 보고 검토를 끝내지 마세요. 저장소 키가 그대로인지, 제목 앞뒤 공백을 없애는 시점이 입력할 때에서 표시할 때로 바뀌지는 않았는지 확인합니다. 새 보조 함수 때문에 전에 보여 주던 오류가 숨겨질 수도 있습니다. 목록을 다시 만드는 과정에서 키보드 포커스(focus)가 사라지지는 않는지도 살펴보세요.

모듈 안에서 쓰는 이름과 저장된 데이터의 속성 이름은 구분해야 합니다. 저장 데이터의 `read`를 `completed`로 바꾸려면 기존 목록을 어떻게 읽을지 결정해야 합니다. 저장 형식을 이전하는 데이터 마이그레이션(migration)에 해당하므로 리팩터링과 별도로 다루세요. 이전 형식에 대한 테스트와 복구 동작을 충분히 검토할 수 있어야 합니다.

브라우저 없이 파싱을 테스트할 수 있게 됐다는 식으로, 현재 코드에서 무엇이 나아졌는지 설명할 수 있는 개선을 고르세요. 범용 저장소 클래스, 이벤트 버스, 플러그인 시스템을 넣으면 코드를 읽는 사람이 이해해야 할 개념도 늘어납니다. 작은 독서 목록에서 그 비용을 감수하려면 막연한 미래 기능보다 구체적인 요구가 있어야 합니다.

## 실습: 너무 큰 제안을 나누기

도우미가 저장 기능 분리, 저장 형식 변경, 검색 추가, 버튼 디자인 변경을 한 패치(patch)에 담자고 합니다. 검토하기 쉬운 단계로 나누고, 첫 단계에서 무엇을 확인할지 적어 보세요.

<details><summary>작업 순서 비교하기</summary>

기존 동작을 유지하면서 저장 기능을 분리하는 일부터 시작하세요. 파싱 테스트와 모듈 가져오기, 저장 실패 처리, 새로고침 후 동작을 확인합니다. 형식 마이그레이션은 이전 형식의 테스트 데이터인 픽스처(fixture)와 복구 계획을 준비해 따로 검토하세요. 검색은 어떤 입력을 일치한다고 볼지 정해 독립된 기능으로 추가하고, 버튼 디자인을 바꿀 때는 키보드 조작과 포커스를 점검합니다. 순서는 달라도 됩니다. 다만 각 패치가 무엇을 위한 것인지 설명할 수 있어야 하고, 그 목적에 맞는 검증 근거도 있어야 합니다.
