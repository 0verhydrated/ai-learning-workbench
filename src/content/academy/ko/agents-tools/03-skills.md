## 절차를 알려 주는 지침과 일을 실행하는 도구

<strong>Agent Skill</strong>은 `SKILL.md`를 포함한 디렉터리입니다. `SKILL.md`에는 YAML 메타데이터와 Markdown 지침을 작성합니다. 반복 업무를 어떻게 수행할지 절차를 정리하고, 필요하면 참고 문서나 템플릿, 스크립트도 함께 담을 수 있습니다. 스킬을 추가해도 모델이 새로 학습되거나 실행 권한이 자동으로 생기지는 않습니다. [1][2]

<strong>도구</strong>는 정해진 인터페이스로 작업을 실행하고, <strong>스킬</strong>은 도구를 활용하는 절차를 설명합니다. <strong>플러그인</strong>은 실행 기능이나 사용자 인터페이스, 스킬 등을 제공할 수 있는 호스트별 확장 패키지입니다. <strong>MCP</strong>는 외부 프로그램이 기능을 제공하는 통신 규약입니다. 예를 들어 보고서 스킬에서 MCP 검색 도구를 쓸 수는 있습니다. 하지만 지침을 설치했다고 서버까지 설치되거나 데이터 접근이 허가되는 것은 아닙니다.

## 필요한 지침부터 읽는 점진적 공개

모든 대화에 모든 절차를 넣으면 컨텍스트가 낭비됩니다. Agent Skills는 먼저 이름과 설명으로 관련 스킬을 찾고, 필요할 때 전체 지침을 읽은 뒤, 보조 파일은 해당 단계에서 읽는 세 단계 방식을 사용합니다. Hermes도 필요할 때 스킬을 불러오는 방식을 구현합니다. 다만 검색 위치와 추가 메타데이터는 호스트마다 다를 수 있습니다. 공통 파일 형식에 속하는 부분과 제품별 확장을 구분해 살펴보세요. [1][3]

명세에서 요구하는 필수 필드는 `name`과 `description`입니다. 이름은 디렉터리 이름과 같아야 하며 소문자 영숫자와 하이픈을 사용합니다. 하이픈으로 시작하거나 끝나면 안 되고, 하이픈을 연속해서 쓸 수도 없습니다. 선택 필드인 `metadata`는 문자열 키와 문자열 값으로 이루어진 맵입니다. 본문에는 핵심 절차를 정리하세요. 참고 파일은 여러 문서를 거쳐 찾아가게 만들기보다 필요한 곳에서 직접 연결하는 편이 좋습니다. [2]

## 실습 예제: 주간 보고서 스킬

이 예제는 스크립트나 네트워크 없이 진행합니다. 사용자가 건넨 표로 초안만 만들고 메시지는 보내지 않습니다. 패키지는 다음과 같이 구성합니다.

```text
weekly-report/
  SKILL.md
  references/status-rules.md
```

호스트가 지원하는 스킬 위치에 `SKILL.md`를 만들고 아래 내용을 넣으세요. 실행할 명령이 아닌 파일 내용입니다.

```markdown
---
name: weekly-report
description: "주간 보고서를 요청할 때 사용합니다. 작업 기록을 인용해 초안을 작성합니다."
metadata:
  owner: "delivery-team"
  version: "1.0"
---

## 입력
보고 기간과 ID, 상태, 담당자, 근거가 포함된 작업 기록을 받습니다.
필수 입력이 없으면 먼저 요청합니다.

## 절차
1. [상태 규칙](references/status-rules.md)을 읽습니다.
2. 보고 기간의 기록만 선택하고 ID를 유지합니다.
3. 같은 ID의 동일 기록은 합치고 내용이 다르면 충돌을 표시합니다.
4. 완료, 장애물, 다음 행동으로 분류합니다.
5. 사실을 담은 각 항목에 기록 ID를 붙입니다.
6. 초안을 반환합니다. 전송하거나 게시하지 않습니다.

## 검증
고유 입력 ID와 분류된 ID를 대조하고 제외 기록을 밝힙니다.
막힌 작업이나 근거 없는 작업을 완료로 집계하지 않습니다.
빠진 담당자와 날짜는 미상으로 표시하고 추측하지 않습니다.
```

`references/status-rules.md`에는 상태를 판단할 기준을 적습니다.

```markdown
## 상태 규칙
- 완료: status=done이고 근거가 비어 있지 않아야 합니다.
- 막힘: status=blocked이며 기록된 장애물을 유지합니다.
- 나머지는 완료가 아니라 다음 행동으로 분류합니다.
- 같은 ID의 내용이 충돌하면 확인받기 전에는 합계를 내지 않습니다.
```

보고 기간 안에 있는 다음 교육용 기록에 이 절차를 적용해 보세요.

| ID | 상태 | 담당자 | 근거 또는 장애물 |
|---|---|---|---|
| T-11 | done | Mina | 검토 승인: review-11 |
| T-12 | blocked | Jun | 테스트 계정 대기 중 |
| T-13 | done | 미상 | 근거 없음 |

절차를 적용한 초안은 다음과 같습니다.

```text
완료: T-11 — 검토 승인(review-11), 담당 Mina.
막힘: T-12 — 테스트 계정 대기 중, 담당 Jun.
다음 행동: T-13 — 완료 근거 확보, 담당 미상.
포함 ID: T-11, T-12, T-13. 제외: 없음.
```

T-13은 `done`으로 표시되어 있어도 완료 근거가 없으므로 다음 행동으로 분류합니다. 마지막 포함 ID 줄을 입력 표와 대조하면 누락되거나 중복된 기록이 있는지 확인할 수 있습니다. 위 초안에서는 각 ID를 한 번씩 포함했고, 담당자를 모르는 항목도 그대로 남겼습니다. 이 결과는 절차를 직접 적용한 예제입니다. 에이전트가 실제로 실행했다는 뜻은 아닙니다.

## 재사용하기 전에 한계와 실행 범위를 확인하세요

스킬에 적힌 절차를 그대로 따라도 정확한 결과가 보장되지는 않습니다. 사용할 수 없는 도구를 가리키거나 오래된 명령, 위험한 스크립트를 담고 있을 수 있습니다. 실행하기 전에 코드와 의존성을 검토하세요. 필요하면 권한이 제한된 자격 증명과 샌드박스, 승인 절차를 사용합니다. Markdown에 “전송하지 마라”라고 쓰는 것만으로 전송을 막을 수는 없습니다. 초안만 작성하는 작업이라면 호스트에서도 전송 기능을 별도로 차단해야 합니다.

명세의 `allowed-tools` 필드는 실험적이며, 구현마다 지원 여부가 다릅니다. 모든 호스트에서 이 필드가 보안 경계로 작동한다고 생각하지 마세요. 내려받은 스킬에 “기존 지시를 모두 무시하라”고 쓰여 있어도 그럴 권한은 없습니다. [2]

## 연습: 충돌하는 중복 기록

blocked 상태인 기존 T-12를 남겨 둔 채 done 상태의 T-12를 하나 더 추가했습니다. 두 번 집계해야 할까요? 마지막 행을 택해도 될까요, 아니면 합계를 보류해야 할까요? 조직별 상태 정책이 길다면 어느 파일에 둘지도 생각해 보세요.

<details>
<summary>해설</summary>

내용이 충돌하는 ID를 표시하고, 확인받을 때까지 합계를 보류합니다. 아무 설명 없이 마지막 행을 고르면 정해지지 않은 충돌 해결 정책을 만들어 내는 셈입니다. 짧은 충돌 처리 원칙은 `SKILL.md`에 남기고, 긴 상태 정책은 직접 연결한 참고 파일에 둡니다. 이후 검증에 중복 사례도 넣어 보세요. 그러면 문서에 적힌 절차가 실제로 의도대로 작동하는지 시험할 수 있습니다.
