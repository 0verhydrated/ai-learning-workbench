## 서로 다른 두 질문

<strong>단위 테스트</strong>는 좁은 소프트웨어 계약을 확인합니다. 예를 들어 파서가 날짜 누락을 거부하는지 검사합니다. <strong>평가</strong>, 즉 eval은 여러 사례에서 모델을 활용한 동작이 작업 기준을 얼마나 충족하는지 측정합니다. 이중 언어 요약이 단서 표현을 유지하고 주장을 올바른 출처에 연결하는지가 그 예입니다. 둘 다 필요합니다. 파서 테스트를 통과했다고 요약의 사실성이 증명되지는 않으며, 그럴듯한 요약을 만들었다고 재시도 처리기가 올바른 것도 아닙니다.

OpenAI 평가 가이드는 작업 정의, 테스트 입력 실행, 결과 분석의 과정을 설명합니다 [1]. 이 방법론은 특정 호스팅 제품과 분리해서 활용할 수 있습니다. 이 수업은 Evals API 연동이 아니라 로컬 평가기를 사용합니다. 호스팅 도구를 선택할 때는 해당 제품이 현재 제공되는지부터 확인하세요.

## 승자를 고르기 전에 데이터셋 만들기

<strong>정답 데이터셋</strong>은 대표 입력과 검토된 기대 답안 또는 평가 기준을 연결합니다. 뉴스라면 출처 발췌문, 발행일, 관련 주장, 허용되는 번역을 보존합니다. 쉬운 영어 발표문만 넣지 말고 평범한 기사, 날짜 충돌, 근거 부족, 프롬프트 인젝션 문구, “예정” 같은 한국어 단서도 포함하세요.

프롬프트 작성자가 반복적으로 튜닝하는 개발용 집합과, 튜닝에 계속 사용하지 않는 별도의 홀드아웃 집합을 나눕니다. 데이터셋, 프롬프트, 모델 식별자, 설정을 함께 버전 관리하세요. 같은 사례로 후보와 기준 버전을 비교하고 변동성이 중요하다면 모델 실행을 반복해 표본을 얻습니다. 평균 점수 하나뿐 아니라 유형별 실패와 불확실성도 보고합니다. 작고 정제된 집합은 회귀를 찾는 데 유용하지만 일반적인 신뢰성을 증명하지는 못합니다.

## 정직한 오프라인 평가 실행하기

다음 표준 라이브러리 프로그램은 <strong>직접 작성한 가상의 픽스처</strong>를 사용합니다. 네트워크 요청도 모델 실행도 하지 않습니다. 의도적으로 약하게 만든 후보는 한 사례에서 단서를 제거하고 다른 사례에서 날짜를 지어냈으므로, 평가기가 두 실패를 찾아야 합니다. 이것은 검사 장치의 테스트이지 모델 성능 측정값이 아닙니다.

```python
fixtures = [
    {"id": "a", "gold": {"date": "2026-11-01", "status": "planned"},
     "candidate": {"date": "2026-11-01", "status": "launched"}},
    {"id": "b", "gold": {"date": "2026-11-02", "status": "launched"},
     "candidate": {"date": "2026-11-02", "status": "launched"}},
    {"id": "c", "gold": {"date": None, "status": "unknown"},
     "candidate": {"date": "2026-11-03", "status": "unknown"}},
]
results = []
for row in fixtures:
    actual, expected = row["candidate"], row["gold"]
    passed = set(actual) == set(expected) and actual == expected
    results.append((row["id"], passed))
assert results == [("a", False), ("b", True), ("c", False)]
print({"passed": sum(ok for _, ok in results), "total": len(results)})
```

결정적 검사는 스키마, 필수 필드, 허용된 식별자, 정확히 추출해야 하는 사실에 적합합니다. 하지만 서술 전체가 근거에 의해 뒷받침되는지는 판정하지 못합니다. 주장과 출처를 연결하는 검토, 완전성·의미 보존·불확실성 표현에 대한 평가 기준을 추가하세요. 모델 심사자를 사용한다면 사람의 라벨과 비교해 보정해야 합니다. 심사자는 긴 답변, 자신의 문체, 답변 순서를 편애할 수 있습니다. 후보의 정체를 숨기고 제시 순서를 무작위화하며 불일치 사례를 검토하세요. 신뢰할 수 없는 후보 답변이 자신의 채점 지침을 정하게 해서는 안 됩니다.

## 실제 실행을 관측하기

<strong>관측 가능성</strong>은 시스템이 내보내는 신호로 내부 동작을 이해하는 능력입니다. OpenTelemetry는 로그, 메트릭, 트레이스를 구분하며, 트레이스는 작업 단위를 나타내는 스팬으로 구성됩니다 [2]. 뉴스 파이프라인에는 실행 전체의 루트 스팬과 수집, 검증, 요약, 출력 검사, 승인, 발행 단계의 하위 스팬을 둡니다.

실행 ID, 단계, 소요 시간, 재시도 횟수, 도구 오류 분류, 프롬프트 버전, 모델 식별자를 기록하세요. 지연 시간 분포, 큐 대기 시간, 검증 실패, 전달 누락을 추적합니다. 토큰 사용량이 제공되면 기록하고, 비용을 계산했다면 버전이 있는 가격표에 근거한 추정값이라고 표시합니다. 사용량이 없으면 0이 아니라 알 수 없음입니다. 도구가 성공 응답을 줬다는 사실만으로 사용자에게 필요한 결과가 도착했다고 볼 수는 없습니다.

관측 데이터에도 개인정보 보호가 필요합니다. 인증 정보, 비공개 원문, 전체 프롬프트, 민감한 쿼리 문자열은 기본적으로 제외합니다. 허용 목록 기반 속성, 접근 제어, 보존 기한, 검토된 마스킹을 사용하세요. 상관관계 ID는 운영 이벤트를 연결해야지 개인정보를 모으는 또 다른 저장소가 되어서는 안 됩니다.
