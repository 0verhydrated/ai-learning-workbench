## 지침과 실행 기능은 다르다

<strong>Agent Skill</strong>은 `SKILL.md`를 포함한 디렉터리입니다. 이 파일은 YAML 메타데이터와 Markdown 지침으로 구성됩니다. 반복 업무를 수행하는 방법, 즉 절차적 지식을 묶으며 참고 문서, 템플릿, 스크립트를 함께 담을 수 있습니다. 스킬을 추가한다고 모델을 새로 학습시키거나 실행 권한을 자동으로 부여하는 것은 아닙니다. [1][2]

네 가지 개념을 구별하세요. <strong>도구</strong>는 정해진 인터페이스로 작업을 실행합니다. <strong>스킬</strong>은 그 도구를 활용할 수 있는 절차를 설명합니다. <strong>플러그인</strong>은 실행 기능, 사용자 인터페이스, 스킬 등을 제공할 수 있는 호스트별 확장 패키지입니다. <strong>MCP</strong>는 외부 프로그램이 기능을 제공하는 통신 규약입니다. 보고서 스킬이 MCP 검색 도구를 사용할 수는 있지만, 지침을 설치하는 것만으로 서버가 설치되거나 데이터 접근이 허가되지는 않습니다.

## 필요한 만큼만 읽는 점진적 공개

모든 대화에 모든 절차를 넣으면 컨텍스트를 낭비합니다. Agent Skills는 이름과 설명으로 관련 스킬을 발견하고, 필요할 때 전체 지침을 읽으며, 보조 파일은 해당 단계에서만 읽는 세 단계 방식을 사용합니다. Hermes도 이러한 요청 시 로딩 방식을 구현합니다. 다만 검색 위치와 추가 메타데이터는 호스트마다 다를 수 있으므로 공통 파일 형식과 제품별 확장을 구분해야 합니다. [1][3]

명세에서 필수 필드는 `name`과 `description`입니다. 이름은 디렉터리 이름과 일치해야 하며 소문자 영숫자와 하이픈을 사용합니다. 하이픈으로 시작하거나 끝날 수 없고 연속 하이픈도 허용되지 않습니다. 선택 필드인 `metadata`는 문자열 키와 문자열 값의 맵입니다. 본문은 핵심 절차에 집중하고, 복잡한 문서 연결망 대신 필요한 참고 파일을 직접 연결하세요. [2]

## 실습 예제: 주간 보고서 스킬

이 예제에는 스크립트나 네트워크가 필요 없습니다. 사용자가 제공한 표를 입력으로 받아 초안만 만들고 메시지를 보내지는 않습니다. 패키지 구조는 다음과 같습니다.

```text
weekly-report/
  SKILL.md
  references/status-rules.md
```

호스트가 지원하는 스킬 위치에 아래 내용의 `SKILL.md`를 둡니다. 아래는 실행 명령이 아니라 파일 내용입니다.

```markdown
---
name: weekly-report
description: "주간 보고서를 요청할 때 사용합니다. 작업 기록을 인용해 초안을 작성합니다."
metadata:
  owner: "delivery-team"
  version: "1.0"
---

## 입력
보고 기간과 ID, 상태, 담당자, 근거가 포함된 작업 기록을 받습니다.
필수 입력이 없으면 먼저 요청합니다.

## 절차
1. [상태 규칙](references/status-rules.md)을 읽습니다.
2. 보고 기간의 기록만 선택하고 ID를 유지합니다.
3. 같은 ID의 동일 기록은 합치고 내용이 다르면 충돌을 표시합니다.
4. 완료, 장애물, 다음 행동으로 분류합니다.
5. 사실을 담은 각 항목에 기록 ID를 붙입니다.
6. 초안을 반환합니다. 전송하거나 게시하지 않습니다.

## 검증
고유 입력 ID와 분류된 ID를 대조하고 제외 기록을 밝힙니다.
막힌 작업이나 근거 없는 작업을 완료로 집계하지 않습니다.
빠진 담당자와 날짜는 미상으로 표시하고 추측하지 않습니다.
```

`references/status-rules.md`에는 실제 판단 기준을 넣습니다.

```markdown
## 상태 규칙
- 완료: status=done이고 근거가 비어 있지 않아야 합니다.
- 막힘: status=blocked이며 기록된 장애물을 유지합니다.
- 나머지는 완료가 아니라 다음 행동으로 분류합니다.
- 같은 ID의 내용이 충돌하면 확인받기 전에는 합계를 내지 않습니다.
```

보고 기간 안에 있는 다음 교육용 기록에 절차를 적용해 봅시다.

| ID | 상태 | 담당자 | 근거 또는 장애물 |
|---|---|---|---|
| T-11 | done | Mina | 검토 승인: review-11 |
| T-12 | blocked | Jun | 테스트 계정 대기 중 |
| T-13 | done | 미상 | 근거 없음 |

초안은 다음과 같아야 합니다.

```text
완료: T-11 — 검토 승인(review-11), 담당 Mina.
막힘: T-12 — 테스트 계정 대기 중, 담당 Jun.
다음 행동: T-13 — 완료 근거 확보, 담당 미상.
포함 ID: T-11, T-12, T-13. 제외: 없음.
```

핵심은 T-13의 처리입니다. `done`이라는 표시만으로는 스킬이 정한 완료 조건을 충족하지 않습니다. 검증은 문장이 자연스러운지만 보는 것이 아니라 모든 기록이 빠짐없이 반영되었는지도 확인합니다. 각 ID는 한 번씩 등장하고, 모르는 담당자를 지어내지 않았습니다. 이는 절차를 직접 적용한 예제이며 에이전트가 실제 실행했다는 주장은 아닙니다.

## 한계와 안전한 재사용

스킬은 일관성을 높일 수 있지만 정확성을 보장하지는 않습니다. 없는 도구를 가리키거나 오래된 명령과 위험한 스크립트를 포함할 수 있습니다. 실행 전에는 코드와 의존성을 검토하고, 필요한 경우 제한된 자격 증명, 샌드박스, 승인 절차를 사용하세요. “전송하지 마라”는 Markdown 문장은 의도를 표현할 뿐입니다. 초안 작성 전용 작업이라면 호스트도 전송 기능을 별도로 차단해야 합니다.

명세의 `allowed-tools` 필드는 실험적이며 지원 여부가 구현마다 다릅니다. 이를 모든 호스트에서 통하는 보안 경계로 생각하지 마세요. 내려받은 스킬이 “기존 지시를 모두 무시하라”고 주장해도 그런 권한은 없습니다. [2]

## 연습: 충돌하는 중복 기록

기존 blocked 상태의 T-12를 유지하면서 done 상태의 T-12를 하나 더 추가했습니다. 두 번 집계해야 할까요, 마지막 행을 택해야 할까요, 아니면 합계를 보류해야 할까요? 긴 조직별 상태 정책은 어디에 두면 좋을까요?

<details>
<summary>해설</summary>

충돌하는 ID를 표시하고 확인받기 전에는 합계를 보류합니다. 조용히 마지막 행을 선택하면 없는 충돌 해결 정책을 만들어 내는 셈입니다. 짧은 충돌 처리 원칙은 `SKILL.md`에 남기고, 긴 상태 정책은 직접 연결한 참고 파일에 둡니다. 이후 검증에도 중복 사례를 포함하면 스킬이 설득력 있는 문서에 그치지 않고 시험 가능한 절차가 됩니다.

</details>
