## 저장된 값도 다시 확인하기

localStorage는 브라우저에서 출처(origin)별로 키와 문자열 값을 저장합니다. JavaScript 배열을 그대로 저장할 수는 없고, 다른 기기로 동기화하거나 영구 백업을 보장해 주지도 않습니다. 브라우저 설정이나 비공개 세션, 사용자의 조작, 용량 제한 때문에 쓰지 못할 수도 있습니다. 한편 같은 출처의 두 페이지는 같은 저장 영역에 접근할 수 있습니다.

키는 `reading-list:v1`처럼 이름 공간(namespace)을 구분해 지으세요. 저장할 때는 `JSON.stringify()`로 배열을 문자열로 직렬화(serialize)하고, 읽을 때는 파싱(parse)해서 값으로 되돌립니다. 파싱에 성공해도 책 목록으로 쓸 수 있다는 뜻은 아닙니다. 올바른 JSON이더라도 값이 `null`이나 숫자일 수 있고, 배열 안의 책 데이터가 잘못됐을 수도 있습니다.

저장 기능을 붙이기 전에 어떤 값을 허용할지 정하세요. 이번 버전은 객체를 담은 배열을 받습니다. 각 책의 식별자는 비어 있지 않은 고유한 문자열이어야 합니다. 제목은 공백 외의 텍스트를 포함한 200자 이하 문자열, 읽음 상태는 불리언이어야 합니다. 문법상 올바른 JSON이어도 목록이 지나치게 크면 렌더링 전에 거부하도록 책의 수도 제한합니다.

## 데이터가 들어오는 경계에서 검증하기

아래 파서(parser)는 책 하나라도 형식에 맞지 않으면 문서 전체를 거부합니다. 잘못된 항목만 조용히 버리지는 않습니다.

```js
export function parseBooks(raw) {
  if (raw === null) return [];
  const value = JSON.parse(raw);
  if (!Array.isArray(value) || value.length > 1000) {
    throw new Error('Invalid reading list');
  }
  const ids = new Set();
  return value.map(book => {
    if (!book || typeof book !== 'object' ||
        typeof book.id !== 'string' || !book.id.trim() ||
        ids.has(book.id) || typeof book.title !== 'string' ||
        !book.title.trim() || book.title.length > 200 ||
        typeof book.read !== 'boolean') {
      throw new Error('Invalid book');
    }
    ids.add(book.id);
    return { id: book.id, title: book.title.trim(), read: book.read };
  });
}
```

필요한 필드만 담아 새 객체를 만들면 예상하지 않은 필드가 앱 상태에 들어오는 것도 막을 수 있습니다. 다만 형식을 검사하는 코드이므로 앱 전반의 보안까지 보장하지는 않습니다. 잘못된 JSON, JSON으로 표현된 `null`, 누락된 필드, 중복 식별자, 유효한 빈 배열을 각각 테스트하세요. 저장된 값이 없어서 전달되는 `null`과 실제로 저장된 문자열 `"null"`은 구분해야 합니다.

## 불러오기 실패와 빈 목록 구분하기

저장소에 접근할 때도, 값을 파싱할 때도 실패할 수 있습니다. 읽기 작업 전체에서 예외를 처리하세요.

```js
export function loadBooks(storage) {
  try {
    return { ok: true, books: parseBooks(storage.getItem('reading-list:v1')) };
  } catch {
    return { ok: false, books: [], error: 'Could not load the saved list.' };
  }
}
```

저장소 객체를 인수로 받으면 테스트에서 작은 가짜 객체(fake)로 바꿔 넣을 수 있습니다. 다만 제한된 환경에서는 `window.localStorage`를 가져오는 순간에도 예외가 날 수 있습니다. 브라우저 어댑터(adapter)에서 저장소를 다음 함수로 넘기기 전에도 이 예외를 처리해야 합니다.

불러오기에 실패해도 빈 목록으로 화면을 띄우면 앱이 멈추지는 않습니다. 다만 그 목록을 바로 저장하면 복구할 수 있는 유일한 사본을 지울 수 있습니다. 불러오기 오류를 별도로 기록하고 복구 안내를 보여 주세요. 사용자가 직접 초기화를 선택하거나 문제를 해결할 때까지 자동 저장을 꺼 두고, 가능하면 원래 저장된 값을 복사하거나 내보낼 방법도 제공합니다. 화면에서도 읽지 못한 목록과 책이 없는 목록을 구분해 알려야 합니다.

## 쓰기 실패를 있는 그대로 알리기

잘 읽었다고 잘 저장되리라는 보장은 없습니다. `setItem()`의 오류를 처리하고 "이번 세션에 추가됨"과 "저장됨"을 구분해 알려 주세요. 메모리에 변경을 남겨 두고 경고를 계속 띄울 수도 있고, 메시지를 보여 주면서 변경을 되돌릴 수도 있습니다. 어느 쪽으로 처리할지 정하고 테스트하세요.

시작할 때 무조건 저장하는 코드는 피하세요. 불러오기 실패 뒤에 실행되면 복구 가능한 유일한 사본까지 지울 수 있습니다. 여러 탭이 서로의 변경을 덮어쓸 수 있다는 한계도 문서에 남깁니다. 이 버전에는 충돌 해결 기능이 없습니다. 저장소 이벤트로 다른 탭에 변경 사실을 알릴 수는 있지만, 충돌하는 편집을 어떻게 합칠지는 별도로 설계해야 합니다.

## 실습: 손상된 데이터 테스트 설계하기

`getItem()`이 `'{broken'`을 반환하는 가짜 저장소 객체를 만드세요. 불러오기 실패를 알리는지, 이어서 실행되는 시작 코드가 `setItem()`을 호출하지 않는지 확인합니다. 쓰기 실패는 별도의 가짜 객체로 테스트하세요. 저장할 때 예외를 던지게 하고, 변경 사항이 저장되지 않았다는 메시지가 나오는지 확인하면 됩니다.

가짜 객체가 쓰기 횟수를 세도록 만들면 불러오기 실패 뒤에 실수로 저장하는지 잡아낼 수 있습니다. 손상된 값을 읽었을 때 경고를 보여 주는지, 원래 값이 보존되는지, 복구 방법을 직접 선택해야 저장이 재개되는지 확인하세요. 쓰기 실패 테스트에서는 저장됐다는 메시지가 나오지 않아야 합니다. 읽기 실패 테스트를 통과했다고 쓰기 실패 안내까지 검증된 것은 아닙니다.
