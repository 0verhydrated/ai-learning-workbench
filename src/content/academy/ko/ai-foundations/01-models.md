## 지금 답하는 것은 무엇일까요?

**모델**은 가중치라고 부르는 수치 매개변수를 학습하여 입력을 예측이나 출력으로 바꾸는 계산 시스템입니다. **앱**은 그 모델을 둘러싼 제품입니다. 채팅 화면, 문서 업로드, 검색, 대화 저장, 권한 관리와 도구가 여기에 포함됩니다. **제공업체**는 모델을 운영하거나 모델에 접근할 수 있게 제공합니다. 한 업체가 여러 모델을 제공할 수도 있고, 한 앱이 요청에 따라 서로 다른 업체의 모델을 사용할 수도 있습니다.

따라서 같은 이름의 모델을 쓰는 제품도 답변이 다를 수 있습니다. 한 제품은 최신 설명서를 검색해서 전달하고, 다른 제품은 질문만 전달할 수 있습니다. 한 제품은 격리된 환경에서 코드를 실행하지만 다른 제품은 코드처럼 생긴 텍스트만 작성할 수도 있습니다. 어떤 모델이 실행됐는지, 어떤 근거를 받았는지, 어떤 도구가 실제로 실행됐는지 구분해서 확인하세요. 유창한 답변만으로는 어느 것도 입증되지 않습니다.

**학습**은 데이터와 학습 목표를 이용해 매개변수를 바꾸는 과정입니다. 사전 학습으로 폭넓은 능력을 얻고, 미세 조정으로 특정 데이터에 대해 추가 학습을 합니다. **추론**은 이미 학습된 모델로 새로운 입력을 처리하는 과정입니다. Hugging Face는 모델 구조인 아키텍처와, 그 구조에 불러오는 특정 가중치인 체크포인트를 구분합니다.[1] 대화 중 문체 안내서를 전달하는 것은 보통 추가 문맥을 이용한 추론이지, 학습 작업이 아닙니다. 서비스가 나중에 제출 데이터를 학습에 활용하는지는 별도의 정책 문제입니다.

## 능력은 순위가 아니라 선택 조건입니다

추론 특화 모델은 답변 전에 어려운 문제를 해결하기 위한 계산을 더 수행할 수 있습니다. 여러 단계에 걸친 버그 분석에는 도움이 될 수 있지만 비용이나 대기 시간이 늘어날 수 있고, 설정 가능한 항목도 모델마다 다릅니다.[2] 더 오래 생각한다고 반드시 맞는 것은 아닙니다. 긴 설명을 증거로 삼지 말고 최종 수정 사항을 테스트하거나 계산 결과를 검증하세요.

멀티모달 모델은 텍스트와 이미지처럼 둘 이상의 형식을 처리합니다. 입력 능력과 출력 능력은 별개입니다. 스크린샷을 받는다고 이미지를 만들거나 음성을 받아쓰는 것은 아닙니다. 화면 오류를 조사할 때 스크린샷은 버튼이 겹친 모습을 보여 주고, 접근성 텍스트와 소스 코드는 픽셀만으로 읽기 어려운 정확한 문구와 동작을 알려 줄 수 있습니다.

로컬 배포는 자신이 관리하는 하드웨어에서 추론을 실행합니다. 오프라인 작업과 데이터 이동 경로 통제에 유리할 수 있지만 메모리, 설치, 업데이트, 보안, 성능을 직접 관리해야 합니다. 클라우드 배포는 상당 부분을 업체에 맡기며 노트북에서 실행하기 어려운 기능을 제공할 수 있지만 네트워크와 업체의 데이터 처리 정책에 의존합니다. 로컬이라는 이유만으로 개인정보가 보호되지는 않습니다. 플러그인, 원격 측정, 외부 도구도 점검해야 합니다. 가중치가 공개됐다고 사용 조건까지 무제한인 것도 아닙니다.

## 선택 사례: 가상의 고객 지원 도우미

문의 분류, 스크린샷 오류 설명, 복잡한 계정 절차의 문제 해결을 모두 지원한다고 해 봅시다. 모든 작업에 가장 비싼 설정을 적용할 필요는 없습니다.

| 작업 | 먼저 시험할 후보 | 합격 기준 |
| --- | --- | --- |
| 짧은 문의 분류 | 저비용 텍스트 모델 | 분류와 출력 형식이 모두 정확함 |
| 스크린샷 해석 | 이미지 입력 지원 모델 | 실제 오류를 읽고 없는 문구를 만들지 않음 |
| 절차 오류 진단 | 추론 특화 모델 | 설명이 로그 및 재현 테스트와 일치함 |

민감 정보를 제거한 작은 평가 자료를 만드세요. 명확한 사례뿐 아니라 애매한 표현, 한국어 문의, 정보가 부족한 질문, 오해하기 쉬운 스크린샷도 넣습니다. 정답은 프롬프트와 분리합니다. 후보마다 동일한 입력과 도구를 제공하고 정확성, 근거 없는 주장, 응답 시간, 비용을 기록하세요. 한 번 우연히 잘 나온 결과를 믿지 말고 반복 측정합니다. 공식 최적화 안내도 실제 입력을 대표하는 평가와 기준 성능 측정부터 시작하도록 권합니다.[3]

**“가장 강력한 모델이 언제나 최선의 제품 선택이다”**라는 생각은 오해입니다. 설명은 훌륭해도 필수 필드를 빠뜨리는 모델이라면, 문의 분류에서는 간단한 모델과 확실한 검증 절차가 더 나을 수 있습니다. 경우에 따라서는 둘 다 쓰지 않고 조회 표로 처리하는 것이 좋습니다.

## 실습: 선택 근거 남기기

오프라인 워크숍에서 가상의 문의를 분류할 도우미를 고르세요. 배포 방식, 필요한 입력 형식, 합격 테스트 하나, 실패 시 처리 방식을 네 줄로 적습니다. 이후 스크린샷 문제 해결이 추가되고 승인된 클라우드 사용이 허용되면 무엇이 달라지는지도 설명하세요.

<details>
<summary>답안 예시</summary>

로컬에서 실행 가능한 텍스트 모델부터 시작하고 라이선스와 하드웨어 요구 사항을 확인합니다. 정답이 있는 문의와 잘못된 입력으로 평가합니다. 허용하지 않은 분류 값은 거부하고, 불확실한 문의는 추측해서 처리하지 말고 사람에게 넘깁니다. 스크린샷이 추가되면 이미지 입력을 지원하는 로컬 모델이나 승인된 클라우드 후보를 평가합니다. 기존 텍스트 모델이 이미지를 볼 수 있다고 가정하면 안 됩니다. 개인정보 규칙을 다시 확인하고 실제 작업 결과를 비교한 후 전환합니다. 이런 측정 없이 특정 모델을 정답으로 고를 수는 없습니다.
