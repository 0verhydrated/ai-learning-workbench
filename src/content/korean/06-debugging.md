## 문제가 생긴 상황부터 기록하기

실패한 이유를 모른 채 "다시 해 봐"라고 요청하면, 원래 코드를 이해하기도 전에 새 코드로 바뀔 수 있습니다. 원래 증상이 사라져도 다른 버그가 생겼다면 어느 수정이 무엇을 해결했는지 알기 어렵습니다. 문제를 재현하는 가장 짧은 순서를 적고 현재 변경 내역부터 살펴보세요.

독서 목록에 책을 추가했는데 곧 사라진다고 해 봅시다. URL과 브라우저, 재현 순서, 화면에서 일어난 일, 콘솔(console) 메시지를 기록하세요. 제출하자마자 페이지 전체가 다시 로드되는지, 직접 새로고침해야 제목이 사라지는지 구분해야 합니다. 전자라면 폼(form)의 기본 페이지 이동을 막지 못했을 가능성이 있습니다. 후자라면 데이터를 저장해 유지하는 영속성(persistence) 기능이 없거나 제대로 작동하지 않을 수 있습니다.

저장된 데이터로 실험하기 전에는 보관할 목록을 복사해 두세요. 가능하면 별도의 테스트용 출처(origin)나 임시 브라우저 프로필을 사용합니다. 디버깅(debugging) 과정에서도 원인을 찾을 근거와 사용자의 실제 독서 목록은 보존해야 합니다.

## 추측하지 말고 이벤트 따라가기

개발자 도구의 Console과 Network 패널에서 `app.js`가 정상적으로 로드되었는지 확인하세요. 스크립트가 빠졌거나 문법 오류가 있거나 선택자(selector)가 틀렸다면 이벤트 리스너(event listener)가 등록조차 안 됐을 수 있습니다. 이때 엉뚱한 곳에 `preventDefault()`를 더 넣어 봐야 해결되지 않습니다.

잠시 관찰용 코드를 넣으면 도움이 될 수 있습니다.

```js
form.addEventListener('submit', event => {
  console.log('submit reached', { prevented: event.defaultPrevented });
  event.preventDefault();
  console.log('navigation prevented', event.defaultPrevented);
  // Existing validation and state update follow here.
});
```

관찰용 코드는 기존 리스너 안에 넣으세요. 핸들러를 하나 더 등록하면 중복 실행 때문에 원인을 잘못 짚을 수 있습니다. 이벤트 메타데이터로 확인할 수 있는 일에 사적인 책 제목까지 기록하지 마세요. 답을 얻었으면 임시 로그는 지우고, 계속 확인할 필요가 있는 조건은 테스트로 남깁니다.

로그를 늘리기보다 중단점(breakpoint)에서 멈춰 보는 편이 나을 때도 많습니다. 핸들러 안에서 입력값과 책 배열을 살펴보고 한 단계씩 실행해 보세요. 화면 갱신을 조사하기 전에 상태부터 바뀌었는지 확인합니다.

## 반증 가능한 가설 하나 세우기

가설을 세웠다면 무엇을 관찰해야 맞는지, 무엇이 나오면 틀린지 말할 수 있어야 합니다. "선택자가 잘못됐다"면 `document.querySelector('#book-form')`이 `null`을 반환할 것으로 예상할 수 있습니다. "다른 출처의 저장소를 사용하고 있다"면 호스트 이름이나 포트가 바뀔 때 저장된 값이 다를 것입니다. 이렇게 예상 결과를 정해 두면 앱을 다시 쓰지 않고도 가설을 확인할 수 있습니다.

도우미에게 근거를 바탕으로 추론하도록 요청하세요.

```text
아직 파일은 바꾸지 마. 폼에서 Enter를 누르면 페이지가 다시 로드돼.
Network를 보니 app.js 요청이 404를 반환했어. HTML은 ./scripts/app.js를
요청하지만, 파일 트리에서는 app.js가 index.html 옆에 있어.
가능성이 높은 원인과 이를 확인할 수 있는 최소한의 검사를 설명해 줘.
관찰된 사실과 가정을 구분해 줘.
```

실패한 요청은 스크립트 경로를 가리킵니다. 폼 라이브러리를 추가해도 그 요청이 실패한 이유는 설명되지 않습니다. 경로를 고친 뒤 의도한 URL을 요청하는지, 핸들러가 실행되는지 확인하세요. 마지막으로 처음 기록한 순서를 반복해 같은 문제가 해결됐는지 봅니다.

## 고친 동작과 그 주변까지 확인하기

문제가 났던 순서대로 다시 실행해 보세요. 이어서 마우스와 키보드로 각각 제출하고, 공백을 입력하고, 책 두 권을 연속으로 추가해 봅니다. 수정한 부분에 순수 로직(pure logic)이 있다면 같은 문제가 재발했을 때 잡을 수 있도록 회귀 테스트(regression test)를 추가하세요. 다만 브라우저의 로드 실패는 브라우저나 HTTP 수준에서 확인해야 합니다. 단위 테스트(unit test)만으로 HTML 경로가 올바르다고 판단할 수는 없습니다.

마지막으로 변경 내역을 읽고, 추측으로 넣었지만 필요 없었던 수정은 걷어 내세요. 증상과 원인, 바꾼 내용, 실제로 실행한 검사를 짧게 남깁니다. 문제를 재현하지 못했다면 그대로 밝히세요. 코드만 읽고 고쳤다고 보고해서는 안 됩니다.

## 실습: 비슷한 두 증상 구분하기

`http://localhost:8000`에서는 새로고침해도 목록이 남아 있는데, `http://127.0.0.1:8000`에서는 빈 목록처럼 보입니다. 원인에 대한 가설을 세우고, 어느 쪽 목록도 지우지 않고 확인할 방법을 제안하세요. 아직 렌더링 함수를 바꾸면 안 되는 이유도 설명해 보세요.
