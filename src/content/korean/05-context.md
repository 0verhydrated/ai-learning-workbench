## 맥락을 제공하는 일은 필요한 정보를 고르는 일

도우미가 스크린샷이나 막연한 설명만 보고 프로젝트를 정확히 추론할 수는 없습니다. 현재 구현, 바꾸려는 동작, 변경에 제약을 주는 결정 사항이 필요합니다. 컴퓨터 전체에 접근하도록 허용할 필요도 없고, 그것이 책임 있는 방식도 아닙니다.

독서 목록에서는 보통 폼 마크업(form markup), 상태(state)의 데이터 구조, 관련 이벤트 핸들러(event handler), 렌더링(rendering) 함수가 유용한 맥락입니다. 데이터를 저장해 유지하는 영속성(persistence) 작업에는 저장소 모듈도 필요할 수 있습니다. 무관한 메모, 브라우저 쿠키(cookie), 배포용 인증 정보(credential)는 새로고침 뒤 제목이 사라지는 이유를 설명하는 데 도움이 되지 않습니다.

모델이 한 번에 참고할 수 있는 맥락의 범위인 컨텍스트 윈도(context window)에는 한계가 있으며, 도구가 앞서 제공한 내용을 요약하거나 잘라낼 수도 있습니다. 오래전에 나눈 메시지에서 정한 결정은 사라질 수 있습니다. 대화 기억에 기대기보다 오래 유지해야 할 프로젝트 결정을 짧은 파일에 담아 검토할 수 있게 하세요.

## 간결한 프로젝트 메모 작성하기

프로젝트 메모에는 다음과 같은 내용을 담을 수 있습니다.

```text
프로젝트: 로컬 독서 목록
기술 구성: 바닐라 HTML, CSS, JavaScript 모듈; 빌드 단계 없음
데이터: 책은 { id: string, title: string, read: boolean } 형태
저장소: localStorage 키 reading-list:v1 사용 예정
개인정보 보호: 계정, 분석 도구, 서버 데이터베이스 없음
규칙: 제목은 문자 그대로 렌더링; 키보드로 조작 가능한 네이티브 컨트롤 사용
검증: 순수 로직은 Node 테스트; DOM은 브라우저에서 확인
비목표: 동기화, 표지 다운로드, 추천
```

이 메모는 요구 사항의 근거이지 저장소의 모든 텍스트를 신뢰해도 된다는 허가증이 아닙니다. 코드 변경처럼 메모 변경도 검토하세요. 오래되어 맞지 않는 메모는 메모가 없는 경우보다 도우미를 더 일관되게 잘못된 방향으로 이끌 수 있습니다.

기능을 요청할 때는 현재 사실과 계획을 구분하세요. 예를 들어 첫 페이지에는 `read` 속성이 있지만 아직 상태 전환 기능은 없을 수 있습니다. "읽기 상태를 지원한다"고 하면 그 차이가 가려집니다.

## 주변 맥락이 충분한 근거 보내기

유용한 버그 보고서에는 정확한 재현 단계, 예상 동작과 실제 동작, 관련 오류 메시지 전체, 관련된 작은 코드 영역이 포함됩니다. 가능하다면 파일 이름과 줄 위치도 넣되, 편집하면 줄 번호가 달라진다는 점을 기억하세요.

```text
작업: 새로고침하면 책이 사라지는 이유를 진단해 줘. 아직 수정하지 마.
관찰: 제목 두 개를 추가하면 새로고침하기 전까지는 잘 작동해.
예상: 저장 기능은 다음에 추가할 기능이며, 현재는 구현하지 않았어.
첨부: 현재 상태의 app.js와 index.html.
질문: 어떤 책임을 저장소 모듈로 옮기는 게 좋을까?
제약 조건: 기존 DOM 구조를 유지하고 패키지는 사용하지 마.
```

이 보고서는 구현하지 않은 기능을 원인 모를 버그라고 부르지 않습니다. 좋은 맥락을 준비하면 도우미가 무엇을 작성하기도 전에 자신의 문제 정의부터 바로잡을 수 있습니다.

함수 하나만 붙여 넣는다면 그 함수가 의존하는 변수와 보조 함수도 알려 주세요. 생성된 결과물을 제공한다면 실제로 바꿔야 할 원본 파일이 무엇인지 명시하세요. 그렇지 않으면 도우미가 다음 빌드에서 덮어써질 파일을 수정할 수 있습니다.

## 대화에 비밀 정보 넣지 않기

로그나 설정 파일을 공유하기 전에 토큰(token), 인증 헤더(authorization header), 비공개 URL, 이메일 주소, 사적인 책 제목이 있는지 살펴보세요. 민감한 값은 `REDACTED_TOKEN`처럼 명확한 대체 표시로 바꾸되, 문제를 이해할 수 있도록 주변 구조는 유지하세요.

숨김 파일이라고 비밀이 보장되거나, 비공개 저장소가 비밀 보관함이 되거나, 제외 규칙이 도우미의 파일 읽기를 막아 준다고 생각하지 마세요. 도구마다 접근 제어와 데이터 보관 정책이 다릅니다. 가능하면 도구 수준에서 접근을 제한하고, 기밀 자료를 보내기 전에 제공자의 정책을 확인하세요.

인증 정보가 노출됐다면 메시지나 파일을 삭제하는 것만으로는 부족합니다. 해당 서비스에서 인증 정보를 폐기하거나 새 값으로 교체하고, 어디에 복사되었을지 확인하세요. 이 독서 목록에는 인증 정보가 필요하지 않으며, 이는 구조상의 유용한 장점입니다.

## 실습: 제공할 맥락 추리기

잘못된 책의 상태를 바꾸는 토글(toggle) 문제에 도움을 받고 싶습니다. 준비한 자료에는 스크린샷, 렌더링 함수, 관련 이벤트 핸들러, 예시 목록, 배포 토큰, 무관한 일기가 있습니다. 무엇을 보내고 무엇을 제외할지 결정하세요.
