## 직접 테스트할 수 있는 규칙 분리하기

유용한 테스트는 의도한 동작이 깨졌을 때 실패하고, 문제를 찾는 데 충분한 정보를 제공합니다. 단순히 함수를 실행하거나 AI 도우미의 출력이 자기 자신과 일치하는지 확인하는 데 그쳐서는 안 됩니다. 이해할 수 있는 규칙부터 시작하세요. 특정 식별자의 읽음 상태를 전환하면 그 책만 바뀌고 원래 배열은 그대로 남아야 합니다.

순수 함수(pure function)를 쓰면 이 규칙을 쉽게 테스트할 수 있습니다. 순수 함수는 문서 객체 모델(DOM), 저장소, 시계, 네트워크 서비스를 읽지 않고 값을 받아 값을 반환합니다. 브라우저 이벤트 처리는 `app.js`에 두고, 데이터 변환은 `books.mjs`로 옮기세요. `.mjs` 확장자는 별도의 패키지 설정 없이도 Node가 파일을 ES 모듈(ES module)로 처리하도록 합니다. 서버가 적절한 JavaScript MIME 유형(MIME type)으로 파일을 보내면 브라우저에서도 가져올 수 있습니다.

## 구현하기 전에 기대 결과 작성하기

`books.test.mjs`를 만들고 다음 테스트를 작성하세요.

```js
import test from 'node:test';
import assert from 'node:assert/strict';
import { toggleBook } from './books.mjs';

test('toggle changes only the requested book without mutation', () => {
  const input = [
    { id: 'a', title: 'Earthsea', read: false },
    { id: 'b', title: 'Kindred', read: true }
  ];
  const before = structuredClone(input);
  const result = toggleBook(input, 'a');

  assert.deepEqual(result, [
    { id: 'a', title: 'Earthsea', read: true },
    { id: 'b', title: 'Kindred', read: true }
  ]);
  assert.deepEqual(input, before);
});
```

`node --test books.test.mjs`를 실행하세요. 모듈이 없다면 가져오기 실패일 뿐, 아직 의미 있는 동작 검증 실패는 아닙니다. 입력을 그대로 반환하는 임시 함수인 스텁(stub)을 만들고 내보낸 뒤 다시 실행하세요. 요청한 상태가 바뀌지 않아 검증문(assertion)이 실패하는지 확인합니다. 이 과정으로 테스트가 빠진 동작을 실제로 감지하는지 알 수 있습니다.

그다음 규칙에 맞는 최소한의 코드를 구현하세요.

```js
export function toggleBook(books, id) {
  return books.map(book =>
    book.id === id ? { ...book, read: !book.read } : book
  );
}
```

테스트를 다시 실행하고 실제 결과를 확인하세요. 이 예제는 구현 제안이지, 여러분의 환경에서 테스트를 통과했다는 보고가 아닙니다. 함수를 애플리케이션으로 가져온 뒤 반환된 배열을 상태에 대입하세요. 반환값을 사용하지 않고 호출만 하면 목록은 갱신되지 않습니다.

## 결과를 달라지게 하는 요인 통제하기

테스트에서는 고정된 식별자를 사용하세요. 무작위 ID를 생성하거나 오늘 날짜에 의존하는 테스트는 검증하려는 규칙과 무관한 이유로 실패할 수 있습니다. 생성 함수에 식별자가 필요하면 인수로 전달하거나 ID 생성기를 주입하세요. 실제 사용 시에는 브라우저와 연결하는 어댑터(adapter)에서 계속 `crypto.randomUUID()`를 호출해도 됩니다.

두 번 전환하는 경우와 존재하지 않는 식별자를 전달하는 경우의 테스트를 추가하세요. 없는 ID를 어떻게 처리할지 명시적으로 정해야 합니다. 여기서는 변경 없이 같은 값을 가진 목록을 반환하는 정책이 합리적입니다. 도우미가 몰래 결정하게 두지 말고, 정한 정책을 테스트하세요.

실제 요구 사항을 표현하는 경우가 아니라면 구현 방식에 종속된 검증문은 피하세요. 인터페이스에서 중요한 것은 다른 책의 값이 그대로 유지되는지이지, 특정 보조 함수가 정확히 한 번 호출되는지는 아닐 수 있습니다. 구현에 지나치게 결합된 테스트는 동작을 바꾸지 않는 리팩터링(refactoring)마저 불필요하게 어렵게 만듭니다.

## 이 테스트로 확인할 수 없는 것 이해하기

Node 내장 테스트 실행기(test runner)는 브라우저 DOM이나 localStorage를 제공하지 않습니다. 이 테스트만으로는 체크박스에 접근 가능한 이름(accessible name)이 있는지, 스크립트 URL이 로드되는지, 화면을 다시 그린 뒤에도 포커스(focus)가 유지되는지 알 수 없습니다. 단위 테스트(unit test)와 함께 짧은 브라우저 점검 목록을 관리하세요. 나중에 브라우저 자동화 도구로 일부 항목을 검사할 수 있지만, 직접 확인하는 과정도 여전히 필요합니다.

도우미에게 빠진 사례를 제안하도록 요청한 뒤, 각 기대 결과를 검토하세요. 생성된 테스트는 생성된 코드와 같은 오해를 반복할 수 있습니다. 검증문을 품질을 증명하는 장식이 아니라 제품의 동작을 결정하는 내용으로 읽으세요.

## 실습: 존재하지 않는 식별자 테스트하기

책 두 권이 있는 목록에서 `missing`의 상태를 전환해도 목록의 값이 원래와 같다는 테스트를 작성하세요. 실행한 다음, 구현에서 식별자 조건을 잠시 제거해 테스트가 실수를 잡아내는지 확인하세요. 확인 후에는 올바른 코드로 되돌리세요.
