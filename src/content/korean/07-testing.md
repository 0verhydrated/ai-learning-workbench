## 직접 테스트할 수 있는 규칙 분리하기

직접 설명할 수 있는 규칙부터 정해 보세요. 특정 식별자의 읽음 상태를 전환하면 그 책만 바뀌고 원래 배열은 그대로 남아야 합니다. 테스트는 둘 중 하나라도 어겼을 때 실패하고, 어떤 기대가 어긋났는지 보여 줘야 합니다. 함수를 호출만 하거나 도우미의 같은 가정으로 만든 결과끼리 비교해서는 의도한 동작을 확인하기 어렵습니다.

이 규칙을 순수 함수(pure function)로 만들면 테스트하기 쉽습니다. 문서 객체 모델(DOM), 저장소, 시계, 네트워크 서비스를 읽지 않고, 받은 값으로 결과를 계산해 반환하는 함수입니다. 브라우저 이벤트 처리는 `app.js`에 남기고 데이터 변환을 `books.mjs`로 옮기세요. Node는 `.mjs` 파일을 별도의 패키지 설정 없이 ES 모듈(ES module)로 처리합니다. 서버가 적절한 JavaScript MIME 유형(MIME type)으로 보내면 브라우저에서도 이 파일을 가져올 수 있습니다.

## 구현하기 전에 기대 결과 작성하기

`books.test.mjs`를 만들고 다음 테스트를 작성하세요.

```js
import test from 'node:test';
import assert from 'node:assert/strict';
import { toggleBook } from './books.mjs';

test('toggle changes only the requested book without mutation', () => {
  const input = [
    { id: 'a', title: 'Earthsea', read: false },
    { id: 'b', title: 'Kindred', read: true }
  ];
  const before = structuredClone(input);
  const result = toggleBook(input, 'a');

  assert.deepEqual(result, [
    { id: 'a', title: 'Earthsea', read: true },
    { id: 'b', title: 'Kindred', read: true }
  ]);
  assert.deepEqual(input, before);
});
```

`node --test books.test.mjs`를 실행하세요. 모듈이 없어서 실패했다면 아직 동작을 검증한 것은 아닙니다. 우선 입력을 그대로 반환하는 임시 함수, 스텁(stub)을 만들고 내보내세요. 다시 실행하면 요청한 책의 상태가 바뀌지 않아 검증문(assertion)이 실패해야 합니다. 그래야 테스트가 구현되지 않은 동작을 실제로 잡아낸다는 것을 알 수 있습니다.

그다음 규칙에 맞는 최소한의 코드를 구현하세요.

```js
export function toggleBook(books, id) {
  return books.map(book =>
    book.id === id ? { ...book, read: !book.read } : book
  );
}
```

테스트를 다시 실행해 결과를 확인하세요. 위 코드는 구현 예시이므로 여러분의 환경에서도 통과하는지는 직접 실행해 봐야 합니다. 앱에서 이 함수를 가져와 사용할 때는 반환된 배열을 상태에 대입하세요. 호출만 하고 반환값을 버리면 목록은 바뀌지 않습니다.

## 테스트와 무관한 변동 줄이기

테스트의 식별자는 고정해 두세요. 무작위 ID나 오늘 날짜를 사용하면 확인하려는 규칙과 관계없는 이유로 실패할 수 있습니다. 생성 함수에 식별자가 필요하다면 인수로 받게 하거나 ID 생성기를 주입하세요. 실제 앱에서는 브라우저와 연결하는 어댑터(adapter)가 계속 `crypto.randomUUID()`를 호출해도 됩니다.

상태를 두 번 전환하면 원래 읽음 상태로 돌아오는지 테스트하세요. 존재하지 않는 식별자를 받았을 때의 규칙도 직접 정해야 합니다. 이 예제에서는 값이 바뀌지 않은 목록을 반환하도록 정할 수 있습니다. 기대 결과를 테스트에 적어 두면 도우미가 알리지 않고 다른 동작을 선택하는 것을 막을 수 있습니다.

다른 책의 값이 그대로인지는 확인해야 합니다. 반면 특정 보조 함수를 정확히 한 번 호출하는지는 요구 사항에 없다면 내부 구현에 속합니다. 그 호출 횟수까지 고정하면 동작을 유지한 채 코드를 재배치할 때도 테스트를 고쳐야 합니다.

## 브라우저에서 확인할 부분 남겨 두기

Node 내장 테스트 실행기(test runner)에는 브라우저 DOM이나 localStorage가 없습니다. 따라서 체크박스에 접근 가능한 이름(accessible name)이 있는지, 스크립트 URL이 로드되는지, 화면을 다시 그려도 포커스(focus)가 유지되는지는 이 테스트로 알 수 없습니다. 단위 테스트(unit test)와 별도로 짧은 브라우저 점검 목록을 두세요. 나중에 일부 항목을 브라우저 자동화 도구로 검사하더라도 직접 확인할 부분은 남습니다.

도우미에게 빠진 사례를 찾아 달라고 하되, 각 검증문이 앱에 어떤 동작을 요구하는지 읽어 보세요. 생성된 코드와 테스트가 같은 오해를 공유할 수도 있습니다. 테스트가 통과했다면 작성한 기대에 부합한다는 근거는 됩니다. 그 기대 자체가 옳은지는 따로 판단해야 합니다.

## 실습: 존재하지 않는 식별자 테스트하기

책 두 권이 담긴 목록에 `missing`을 전달해 상태를 전환해 보세요. 목록의 값이 그대로인지 확인하는 테스트를 작성해 실행합니다. 그런 다음 구현에서 식별자 조건을 잠시 빼고 테스트가 이 실수를 잡는지 확인하세요. 확인을 마치면 올바른 코드로 되돌려 놓으세요.

<details><summary>검증문 확인하기</summary>

고정된 책 데이터로 `assert.deepEqual(toggleBook(input, 'missing'), input)`을 검사하세요. 식별자 조건을 뺀 구현은 책들의 상태를 바꾸므로 이 검증에서 실패해야 합니다. 그래도 통과한다면 테스트 파일이 실제로 실행됐는지, 입력으로 빈 배열을 넣지는 않았는지 살펴보세요. 실행한 결과도 기록합니다. 테스트는 작성만 해서는 제대로 작동하는지 알 수 없습니다.
