## 작업을 맡기되 주도권은 넘기지 않기

코딩 에이전트(coding agent)는 채팅 도우미보다 적은 감독만으로 파일을 살피고, 코드를 수정하고, 명령을 실행하며, 이 과정을 반복할 수 있습니다. 자율성이 있는 만큼 작업 경계를 더 명확하게 정해야 합니다. 에이전트는 수정 가능한 파일, 성공으로 인정할 기준, 승인이 필요한 행동을 알아야 합니다.

독서 목록에서 손상된 저장 데이터에 대한 테스트를 추가하는 일은 위임하기에 적절합니다. "원하는 대로 앱을 개선해 줘"는 그렇지 않습니다. 첫 번째 작업에는 정해진 인터페이스와 관찰 가능한 결과가 있지만, 두 번째 요청은 제품에 관한 결정, 의존성 변경, 광범위한 재작성을 유도합니다.

작업에 맞춰 권한을 선택하세요. 테스트를 작성하는 에이전트에게는 배포 권한, 개인 문서, 브라우저 세션, 운영 환경 인증 정보(credential)가 필요하지 않습니다. 도구의 권한 제어는 에이전트에게 조심하라고 적어 둔 문장보다 강한 제한을 제공합니다. 물론 둘 다 유용할 수 있습니다.

## 동시에 수정할 때 워크트리 사용하기

Git 워크트리(worktree)는 하나의 저장소에서 서로 다른 브랜치(branch)를 각각 별도 작업 디렉터리에 체크아웃(checkout)할 수 있게 합니다. 여러분과 에이전트가 동시에 작업할 때 실수로 서로의 작업을 건드릴 가능성을 줄여 줍니다. 독서 목록 저장소에서 현재 상태를 확인한 뒤 다음과 같이 실행할 수 있습니다.

```sh
git status --short
git worktree add ../reading-list-storage-tests -b agent/storage-tests
```

새 디렉터리는 현재 커밋된 리비전(revision)에서 시작합니다. 원래 디렉터리의 커밋되지 않은 변경 사항은 자동으로 포함되지 않습니다. 따라서 기준으로 삼을 변경을 먼저 커밋하거나, 그 변경은 제외된다고 설명하세요. 에이전트가 비슷한 이름의 디렉터리를 찾게 두지 말고 정확한 워크트리 경로를 알려 주세요.

워크트리는 샌드박스(sandbox)가 아닙니다. 저장소 메타데이터(metadata)를 공유하며, 프로세스가 접근 가능한 다른 파일을 읽거나 네트워크를 사용하는 일을 막지 않습니다. 더 강한 경계가 필요하면 운영 체제나 도구 수준의 격리를 사용하세요. 디렉터리가 나뉘어 있어도 같은 인터페이스를 바꾸는 두 작업 사이의 논리적 충돌까지 막을 수는 없습니다.

## 실행 가능한 위임 지시서 작성하기

```text
작업: parseBooks와 loadBooks에 대해 결과가 일정한 테스트를 추가하세요.
워크트리: ../reading-list-storage-tests
허용되는 변경: storage.test.mjs만 수정하세요.
테스트 사례: 유효한 빈 목록, 잘못된 JSON, 중복 ID, 잘못된 필드 자료형,
getItem이 예외를 던지는 저장소 객체.
애플리케이션 코드를 바꾸거나, 패키지를 설치하거나, 비밀 정보에 접근하거나,
무언가를 공개하지 마세요. 현재 API 때문에 테스트할 수 없다면 보고하세요.
node --test storage.test.mjs를 실행하고 실제 출력과 한계를 보고하세요.
마지막에 변경한 파일, 가정, 검증하지 못한 동작을 정리하세요.
```

이 지시서는 작업이 허용 범위를 벗어날 때 멈출 기준을 제공합니다. 그렇지 않으면 에이전트가 "도와주려는" 마음에 편리한 테스트를 통과시키려고 파서(parser)를 바꿀 수도 있습니다. 범위를 넓혀 달라는 요청은 원래 목표에 비추어 검토하세요.

서로 독립적인 작업을 병렬로 진행하세요. 같은 파일을 수정하지 않는다면 한 에이전트는 접근성(accessibility)을 살피고 다른 에이전트는 파서 테스트를 작성할 수 있습니다. 여러 에이전트에게 공통 데이터 형식을 각자 재설계하도록 맡긴 뒤, 자동 통합이 의견 차이를 해결해 줄 것이라고 기대해서는 안 됩니다.

## 작업을 검토한 뒤 통합하기

변경분(diff)을 직접 읽으세요. 검증문(assertion)이 의도한 동작을 표현하는지, 테스트가 실제로 실행되었는지, 테스트를 건너뛰거나 기대 조건을 약화해 실패를 숨기지 않았는지 확인하세요. 두 번째 에이전트에게 패치를 검토하게 할 수도 있지만, 에이전트끼리 동의했다는 사실만으로 정확성이 독립적으로 입증되지는 않습니다.

브랜치를 승인한 뒤에는 의도한 통합 브랜치로 병합(merge)하고 그곳에서 관련 검사를 다시 실행하세요. 분리된 워크트리에서 통과한 테스트도 다른 곳에서 만든 변경과 합쳐지면 실패할 수 있습니다. 공개는 병합과 별개로 다루세요. 테스트를 통과했다고 해서 에이전트에게 배포 권한이 생기는 것은 아닙니다.

`git worktree remove`로 제거하기 전에 워크트리에 커밋되지 않은 변경이 있는지 확인하세요. 강제 제거는 미완성 작업을 버릴 수 있으므로 평소 정리 방식으로 삼지 마세요. 유용한 발견은 에이전트의 임시 세션 기억에 의존하지 말고 프로젝트 문서에 남기세요.

## 실습: 승인이 필요한 경계 정하기

저장 기능 테스트를 작성하던 에이전트가 브라우저 자동화 패키지 설치와 배포 토큰(token) 읽기 권한을 요청합니다. 두 요청이 작업 범위에 맞는지 판단하고, 대신 어떤 검증 근거를 원하는지 명시하세요.

순수 파서와 저장소 어댑터(adapter)를 테스트하는 데는 두 요청 모두 필요하지 않습니다. Node 내장 테스트 실행기와 주입한 가짜 저장소를 사용하라고 요청하세요. 자동화할 만한 브라우저 전용 동작을 발견했다면, 필요한 의존성과 권한의 부담을 포함해 별도 제안으로 기록하세요. 배포 토큰은 이 테스트 작업에 아무 역할도 없으므로 접근할 수 없는 상태로 유지해야 합니다.
