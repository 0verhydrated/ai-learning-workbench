## 구조를 바꾸기 전에 문제부터 정의하기

리팩터링(refactoring)은 의도한 외부 동작을 유지하면서 내부 구조를 바꾸는 작업입니다. 다음 기능을 더 쉽게 만들도록 도와줄 수는 있지만, "전부 정리해 줘"는 좋은 지시가 아닙니다. 중복된 검증, 여러 책임이 뒤섞인 처리 함수(handler), 브라우저 없이 테스트할 수 없는 저장 로직처럼 구체적으로 불편한 지점을 찾아야 합니다.

이제 독서 목록에는 폼, 데이터 변환, 화면 표시, 영구 저장 기능이 있습니다. 그래도 파일 하나로 충분히 이해할 수 있는 크기일 수 있습니다. 파일 수를 늘리기 위해 나누지는 마세요. 코드 사이의 의존 정도인 결합도(coupling)를 줄이거나 테스트하기 좋은 접점을 만들 수 있을 때 경계를 분리하세요.

처음 분리할 대상으로는 저장 기능의 경계가 실용적입니다. JSON 파싱과 검증을 모듈(module)로 옮기면 Node에서 직접 테스트할 수 있습니다. localStorage를 가져오고 오류를 표시하는 책임은 브라우저 어댑터(adapter)에 남겨 두면 됩니다.

## 유지하려는 동작 확인하기

수정 전에 기존 테스트를 실행하고 실패한 항목을 기록하세요. 브라우저 흐름도 확인합니다. 책을 추가하고, 읽음 상태를 전환하고, 새로고침한 뒤 키보드로 조작 요소를 사용해 보세요. 동작이 문서화되어 있지 않다면 현재 코드가 하는 일을 기록하는 특성화 테스트(characterization test)를 작성하세요. 그런 다음 그 동작이 정말 바람직한지 판단합니다.

특성화 테스트가 기록했다는 이유만으로 이미 알려진 버그를 유지하지는 마세요. 그 버그를 고치는 것은 별도의 기대 결과가 필요한 동작 변경입니다. 이 구분을 명확히 하면 검토자가 차이가 의도된 것인지 실수인지 알아보기 쉽습니다.

Git으로 작업 시작 상태를 확인하세요.

```sh
git status --short
git diff
node --test books.test.mjs
```

관련 없는 로컬 작업을 덮어쓰지 마세요. 함께 사용하는 코드를 옮기기 전에는 확인된 상태를 커밋(commit)하거나 작업한 사람과 조율하세요. 작업 트리(working tree)가 깨끗하면 편리하지만, 더 중요한 것은 어떤 변경이 이번 작업에 속하는지 파악하는 일입니다.

## 한 번에 하나의 책임만 옮기기

범위를 좁힌 프롬프트(prompt)는 다음과 같이 작성할 수 있습니다.

```text
parseBooks를 storage.mjs로 분리하세요. 허용하는 형식, 오류 동작,
저장소 키는 바꾸지 마세요. 가져오기 구문과 테스트를 갱신하세요.
화면 표시를 바꾸거나 DOM ID의 이름을 변경하거나 의존성을 추가하거나
데이터 마이그레이션을 도입하지 마세요. 변경분과 실제 테스트 결과를 보여 주세요.
동작을 바꿔야 한다면 작업을 멈추고, 진행하기 전에 이유를 설명하세요.
```

먼저 함수를 옮기고 가져오기 구문을 수정하세요. 해당 부분의 테스트를 실행합니다. 그다음 실행 가능한 전체 테스트 모음을 돌리고, 모듈 경로의 영향을 받는 브라우저 동작도 점검하세요. 분리한 함수 자체는 완벽히 보존했더라도 가져오기 경로의 오타 때문에 페이지가 작동하지 않을 수 있습니다.

다음 단계에서는 제출 처리 함수를 입력 정규화(normalization), 상태 변환, 화면 표시, 저장 결과 알림으로 나눌 수 있습니다. 순서를 명확히 유지하세요. 보조 함수가 충분한 정보를 반환하지 않는 바람에 저장 실패가 성공 상태 메시지로 바뀌어서는 안 됩니다.

## 숨은 동작 변경 검토하기

서식만 살피지 마세요. 저장소 키가 바뀌었나요? 제목 앞뒤 공백 제거 시점이 입력할 때에서 화면에 표시할 때로 옮겨졌나요? 새 보조 함수가 이전에는 인터페이스에 표시하던 오류를 숨기나요? 무해해 보이는 목록 재생성이 키보드 포커스(focus)를 없앴나요?

모듈 내부의 이름을 바꾸는 것과 직렬화된 속성 이름을 바꾸는 것은 다릅니다. 저장된 데이터에서 `read`를 `completed`로 바꾸려면 기존 목록과의 호환성을 결정해야 합니다. 이는 단순한 정리가 아니라 데이터 마이그레이션(migration), 즉 저장 형식을 이전하는 작업입니다. 이전 형식 테스트와 복구 동작을 충분히 검토하도록 리팩터링과 분리하세요.

가상의 미래 기능을 위해 복잡한 추상화(abstraction)를 만드는 것보다, 설명할 수 있는 작은 개선을 택하세요. 범용 저장소 클래스(repository class), 이벤트 버스(event bus), 플러그인 시스템(plugin system)은 구체적인 요구 사항이 없다면 이 작은 독서 목록을 오히려 이해하기 어렵게 만듭니다.

## 실습: 너무 큰 제안을 나누기

도우미가 저장 기능 분리, 저장 형식 변경, 검색 추가, 버튼 디자인 변경을 하나의 패치(patch)로 제안합니다. 검토 가능한 단계로 나누고 첫 단계에서 무엇을 점검할지 적어 보세요.

<details><summary>작업 순서 비교하기</summary>

동작을 유지하는 저장 기능 분리부터 시작하고 파싱 테스트, 모듈 가져오기, 저장 실패, 새로고침 후 동작을 검증하세요. 형식 마이그레이션은 이전 형식의 테스트 데이터인 픽스처(fixture)와 복구 계획을 준비해 별도로 검토합니다. 검색은 일치 규칙을 명확히 정해 독립된 기능으로 추가하세요. 버튼 디자인 변경은 키보드 조작과 포커스를 점검하며 검토하세요. 순서는 달라도 되지만, 각 패치에는 설명 가능한 목적 하나와 그 목적에 맞는 검증 근거가 있어야 합니다.
