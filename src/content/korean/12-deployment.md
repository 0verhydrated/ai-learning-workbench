## 브라우저에 필요한 것만 공개하기

독서 목록은 정적 애플리케이션(static application)입니다. 호스트(host)가 HTML, CSS, JavaScript를 제공하고, 방문자의 브라우저가 상호작용과 localStorage를 처리합니다. 이 설계에는 애플리케이션 서버나 데이터베이스가 필요하지 않습니다. 배포 과정을 확인할 수 있고 이전 배포본으로 복원할 수 있는 정적 호스팅 서비스를 선택하세요.

페이지, 스타일, 브라우저 모듈(module), 필요한 리소스(asset)를 담은 배포 디렉터리를 준비하세요. 저장소 메타데이터(metadata), 인증 정보(credential), 개인 메모, 개발 전용 파일을 실수로 업로드하지 마세요. 호스팅 서비스가 저장소에서 바로 배포한다면 저장소 루트가 적절할 것이라고 가정하지 말고 배포 디렉터리 설정을 확인하세요.

배포본을 만들기 전에 테스트와 로컬 브라우저 점검 목록을 실행하세요. 배포하려는 커밋(commit)을 기록합니다. 업로드 성공은 파일이 받아들여졌다는 뜻일 뿐, 배포된 페이지가 작동한다는 증거는 아닙니다.

## 배포 경로에서 직접 테스트하기

어떤 호스팅 서비스는 도메인 루트에 배포하고, 어떤 서비스는 `/reading-list/` 같은 프로젝트 경로 접두사(prefix)를 사용합니다. 루트 상대 경로(root-relative path)는 도메인 루트에서 시작하므로, 프로젝트 경로 아래에서는 잘못된 위치를 가리킬 수 있습니다.

```html
<!-- 문서가 있는 디렉터리를 기준으로 하는 상대 경로 -->
<link rel="stylesheet" href="./styles.css">
<script type="module" src="./app.js"></script>
```

JavaScript 모듈 내부의 가져오기 경로는 가져오는 쪽 모듈의 URL을 기준으로 해석됩니다. 그 경로도 파일 이름의 대소문자까지 확인하세요. 로컬 파일 시스템에서는 허용되는 차이를 호스트에서는 허용하지 않을 수 있습니다. `.mjs` 확장자를 사용했다면 호스트가 해당 파일을 JavaScript MIME 유형(MIME type)으로 제공하는지 확인하세요.

정확한 공개 URL을 열고, 개발자 도구의 Network 패널에서 실패한 요청을 살핀 뒤 그 주소에서 직접 새로고침하세요. 프로젝트 디렉터리 주소 끝의 슬래시(trailing slash)를 호스트가 어떻게 처리하는지도 확인합니다. 디렉터리 URL을 파일 URL로 취급하면 상대 링크가 다르게 해석될 수 있습니다. `base` 요소는 문서 전체에서 여러 URL의 해석 방식을 바꾸므로 가볍게 추가하지 마세요.

## 브라우저 설정은 공개 정보로 다루기

일반적인 브라우저 스크립트는 터미널의 환경 변수(environment variable)에 자동으로 접근할 수 없습니다. 빌드 도구(build tool)가 설정값을 결과물에 치환해 넣을 수는 있지만, 브라우저로 전달하는 것은 무엇이든 방문자에게 보입니다. 이름이 `SECRET`인 변수도 치환된 뒤에는 비밀로 남지 않습니다.

이 애플리케이션에는 API 키가 필요하지 않습니다. 나중에 비공개 인증 정보가 필요한 기능을 추가한다면 신뢰할 수 있는 서버 측 경계를 두거나 설계를 바꿔야 합니다. 키를 JavaScript나 localStorage에 넣어 해결하려고 하지 마세요.

배포한 사이트는 로컬 서버와 출처(origin)도 다릅니다. 개발 중에 만든 목록이 온라인에 자동으로 나타나지는 않습니다. 이를 데이터 손실로 취급하지 말고 이유를 설명하세요. 호스트 이름이 다른 미리보기 배포도 저장소가 분리됩니다. 반면 같은 출처의 경로 접두사들은 localStorage를 공유합니다. 그래서 이름 공간(namespace)을 구분하는 키가 중요합니다.

## 사람들이 배포본을 사용할 수 있는지 검증하기

배포한 페이지에서 제목을 추가하고 읽음 상태를 전환한 다음 새로고침해 저장 상태를 확인하세요. 유효하지 않은 제목과 마크업(markup)처럼 보이지만 글자 그대로 표시해야 하는 제목도 입력해 보세요. 키보드만으로 테스트하세요. 포커스(focus)가 보여야 하고, 조작 요소의 이름이 이해하기 쉬워야 하며, 갱신 뒤 포커스 위치도 자연스러워야 합니다.

좁은 화면과 브라우저 확대 상태에서도 확인하세요. 잘린 조작 요소, 가로 스크롤, 읽기 어려운 명암 대비, 색상에만 의존하는 상태 메시지가 있는지 살펴보세요. 자동 접근성(accessibility) 검사는 일부 문제를 찾을 수 있지만, 상호작용이 이해하기 쉬운지까지 보장하지는 못합니다. 가능하다면 보조 기술(assistive technology)로 페이지를 읽어 보고, 실제로 확인한 내용을 기록하세요.

## 필요해지기 전에 롤백 계획 세우기

정상 동작이 확인된 배포본이나 커밋을 보관하고 호스팅 서비스의 복원 절차를 익혀 두세요. 새 배포본에서 로딩이 깨지면 해당 버전을 복원하고 공개 URL을 다시 검증하세요. 캐시(cache) 때문에 방문자가 이전 파일을 계속 받을 수 있으므로, 한 번 새로고침한 결과만 믿지 말고 요청되는 리소스를 확인하세요.

코드를 이전 버전으로 되돌리는 롤백(rollback)은 localStorage까지 되돌리지 않습니다. 앞으로 데이터 형식 마이그레이션(migration)을 하면 이전 코드가 새 데이터를 읽지 못할 수 있습니다. 마이그레이션은 별도 작업으로 분리하고, 호환성을 테스트하며, 저장 형식을 바꾸기 전에 복구나 내보내기 기능을 제공하세요. 이 강좌의 버전이 포함된 키는 그런 결정을 명시적으로 드러내지만, 마이그레이션을 자동으로 해결하지는 않습니다.

## 실습: 배포 기록 작성하기

배포 URL, 소스 커밋, 수행한 점검, 알려진 한계, 롤백 대상을 기록하세요. 독서 목록 데이터가 어디에 저장되는지도 한 문장으로 적으세요.
