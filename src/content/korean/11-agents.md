## 작업을 맡기되 주도권은 넘기지 않기

코딩 에이전트는 채팅 도우미보다 적은 개입으로 파일 읽기, 코드 수정, 명령 실행을 반복할 수 있습니다. 시작하기 전에 바꿔도 되는 파일, 완료를 판단할 근거, 승인이 필요한 행동을 정하세요. 범위가 없으면 작은 요청도 허락하지 않은 변경으로 이어질 수 있습니다.

독서 목록의 손상된 저장 데이터를 다루는 테스트는 맡겨 볼 만한 작업입니다. 사용할 인터페이스가 정해져 있고 결과도 확인할 수 있습니다. 반면 "원하는 대로 앱을 개선해 줘"라고 하면 제품 방향을 결정하거나 의존성을 바꾸고 코드를 대대적으로 다시 쓰는 데까지 번질 수 있습니다.

권한도 작업에 맞춰 주세요. 테스트를 작성하는 데 배포 권한이나 개인 문서, 브라우저 세션, 운영 환경 인증 정보(credential)는 필요하지 않습니다. 조심하라는 지시도 도움이 될 수 있지만, 도구에서 접근 권한을 제한하는 편이 더 강하게 통제할 수 있습니다. 가능하면 함께 사용하세요.

## 동시에 수정할 때 워크트리 사용하기

Git 워크트리(worktree)를 쓰면 같은 저장소의 서로 다른 브랜치(branch)를 별도 작업 디렉터리에 체크아웃(checkout)할 수 있습니다. 여러분과 에이전트가 동시에 작업해도 서로의 파일을 실수로 건드릴 가능성이 줄어듭니다. 독서 목록 저장소의 현재 상태를 확인한 뒤 다음 명령을 실행할 수 있습니다.

```sh
git status --short
git worktree add ../reading-list-storage-tests -b agent/storage-tests
```

새 디렉터리는 현재 커밋된 리비전(revision)에서 시작합니다. 원래 디렉터리에 남아 있는 미커밋 변경은 자동으로 따라오지 않습니다. 작업의 기준에 포함할 변경은 먼저 커밋하거나, 이번에는 그 변경을 제외한다고 설명하세요. 에이전트가 비슷한 이름의 폴더를 찾아다니지 않도록 워크트리 경로도 정확히 알려 주세요.

워크트리를 샌드박스(sandbox)로 생각하면 안 됩니다. 저장소 메타데이터(metadata)를 공유하고, 프로세스가 읽을 수 있는 다른 파일이나 네트워크에 대한 접근도 차단하지 않습니다. 더 강하게 격리해야 한다면 운영 체제나 도구에서 제공하는 기능을 쓰세요. 디렉터리를 나눠도 같은 인터페이스를 서로 다르게 바꾸는 논리적 충돌은 생길 수 있습니다.

## 할 일과 멈출 조건을 함께 적기

```text
작업: parseBooks와 loadBooks에 대해 결과가 일정한 테스트를 추가하세요.
워크트리: ../reading-list-storage-tests
허용되는 변경: storage.test.mjs만 수정하세요.
테스트 사례: 유효한 빈 목록, 잘못된 JSON, 중복 ID, 잘못된 필드 자료형,
getItem이 예외를 던지는 저장소 객체.
애플리케이션 코드를 바꾸거나, 패키지를 설치하거나, 비밀 정보에 접근하거나,
무언가를 공개하지 마세요. 현재 API 때문에 테스트할 수 없다면 보고하세요.
node --test storage.test.mjs를 실행하고 실제 출력과 한계를 보고하세요.
마지막에 변경한 파일, 가정, 검증하지 못한 동작을 정리하세요.
```

이 지시에는 현재 API로 테스트할 수 없으면 파서를 고치지 말고 보고하라는 중단 조건이 있습니다. 범위를 넓혀 달라는 요청이 오면 기존 동작을 테스트하는 데 꼭 필요한지 검토하세요. 테스트 작성 권한만으로 테스트 대상의 동작까지 바꿔도 되는 것은 아닙니다.

같은 파일을 고치지 않는 접근성 점검과 파서 테스트는 병렬로 맡길 수 있습니다. 다만 공통 설계는 먼저 조율해야 합니다. 여러 에이전트가 데이터 형식을 제각각 바꾸면 파일을 병합해도 책 데이터에 대한 서로 다른 가정은 해결되지 않습니다.

## 작업을 검토한 뒤 통합하기

변경분을 직접 읽고 검증문을 요청한 동작과 대조하세요. 실제 테스트 출력에서 건너뛴 사례를 확인하고, 실패를 숨기려고 기대 조건을 느슨하게 만들지는 않았는지도 살펴봅니다. 다른 에이전트에게 검토를 맡길 수 있지만, 둘이 동의한다는 사실만으로 코드의 정확성이 독립적으로 입증되지는 않습니다.

검토해 승인한 브랜치는 합치기로 한 통합 브랜치에 병합(merge)하고 관련 검사를 다시 실행하세요. 별도 워크트리에서는 통과해도 다른 변경과 합친 뒤에는 실패할 수 있습니다. 공개 여부는 병합과 따로 결정해야 합니다. 테스트 통과를 에이전트의 배포 승인으로 간주하지 마세요.

`git worktree remove`를 실행하기 전에 커밋하지 않은 변경이 남았는지 확인하세요. 강제로 지우면 미완성 작업을 잃을 수 있으므로 습관처럼 사용하지 마세요. 작업 중 알아낸 유용한 내용은 프로젝트 문서에 남깁니다. 에이전트의 임시 세션 기억에만 맡겨 두면 나중에 다시 참고하기 어렵습니다.

## 실습: 승인이 필요한 경계 정하기

저장 기능 테스트를 작성하던 에이전트가 브라우저 자동화 패키지를 설치하고 배포 토큰(token)을 읽게 해 달라고 합니다. 각각 이번 작업에 필요한지 판단하고, 대신 어떤 방법으로 검증해 결과를 보여 달라고 할지 적어 보세요.

<details><summary>경계 확인하기</summary>

순수 파서와 저장소 어댑터(adapter)를 테스트하는 데는 둘 다 필요하지 않습니다. Node 내장 테스트 실행기와 주입한 가짜 저장소로 검증해 달라고 하세요. 자동화할 만한 브라우저 전용 동작을 발견했다면 별도 제안으로 남깁니다. 추가할 의존성과 필요한 권한도 함께 검토해야 합니다. 배포 토큰은 이 테스트에 쓰이지 않으므로 계속 접근을 차단해 두세요.
