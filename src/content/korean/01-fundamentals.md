## 무엇을 책임져야 하는지 정하기

바이브 코딩(vibe coding)은 흔히 원하는 결과를 설명하고, 생성된 변경 사항을 받아들인 뒤, 화면이 그럴듯한지 보고 성공 여부를 판단하는 방식을 말합니다. 한 번 쓰고 버릴 실험에는 유용할 수 있습니다. 하지만 무엇이 바뀌었는지 설명할 수 없거나, 오류를 재현하거나 누군가의 데이터를 복구할 수 없다면 위험해집니다. 인터페이스가 그럴듯해도 새로고침 한 번에 독서 목록이 사라질 수 있습니다.

책임 있는 AI 보조 개발은 빠른 피드백을 유지하면서도 개발자가 책임을 지는 방식입니다. 동작을 정하고, 변경 사항을 살펴보고, 검사를 실행한 뒤, 그 근거가 배포를 뒷받침하는지 판단해야 합니다. 도우미는 코드를 제안하고 낯선 문법을 설명할 수 있습니다. 그러나 제품에 관한 결정을 대신 내릴 수는 없으며, 확신에 찬 설명이 테스트 결과를 대신하지도 않습니다.

이 과정에서는 별도 프레임워크 없이 사용하는 바닐라(vanilla) HTML, CSS, JavaScript로 독서 목록을 만듭니다. 사용자는 책 제목을 추가하고, 읽은 책을 표시하고, 브라우저의 로컬 저장소인 localStorage로 같은 브라우저에 목록을 보관합니다. 계정, 공유 목록, 서버 데이터베이스는 없습니다. 이 경계를 명확히 하면 프로젝트를 이해할 수 있을 만큼 작게 유지할 수 있습니다.

## 브라우저의 역할 분담 이해하기

HTML은 폼(form), 입력란, 버튼, 목록처럼 의미와 구조를 표현합니다. CSS는 간격과 눈에 보이는 키보드 포커스(focus)를 비롯한 표시 방식을 제어합니다. JavaScript는 이벤트(event)를 처리하고, 애플리케이션 상태(state)를 바꾸고, 문서를 갱신합니다. 문서 객체 모델(DOM, Document Object Model)은 브라우저가 이 문서를 객체로 표현한 것입니다.

클릭할 수 있어 보이는 버튼이 실제로 작동하는 조작 요소인 것은 아닙니다. 키보드로도 활성화할 수 있는 실제 `button` 요소를 우선 사용하세요. JavaScript 배열(array)에 저장한 제목은 자동으로 화면에 나타나지 않습니다. 프로그램이 DOM에 렌더링(rendering), 즉 화면에 표시될 형태로 반영해야 합니다. 배열이 영구히 유지되는 것도 아닙니다. 페이지를 새로고침하면 JavaScript가 처음부터 다시 실행됩니다.

```js
const books = [
  { id: 'book-1', title: 'A Wizard of Earthsea', read: false }
];

const unread = books.filter(book => !book.read);
console.log(unread.map(book => book.title));
```

이 예제는 객체(object)를 담은 배열을 정의합니다. 각 객체에는 변하지 않는 식별자(identifier), 문자열(string) 제목, 참과 거짓으로 읽기 상태를 나타내는 불리언(boolean) 값이 있습니다. 필터는 조건에 맞는 객체를 담은 새 배열을 만들 뿐, 아무것도 저장하지 않습니다. 브라우저 콘솔(console)에서 실행하기 전에 그 배열에 무엇이 들어 있을지 예상해 보세요.

## 하나의 변경이 시스템을 거치는 과정 따라가기

사용자가 제목을 제출할 때 의도한 흐름은 다음과 같습니다. 폼 이벤트를 받고, 입력값의 앞뒤 공백을 제거해 검증하고, 책을 만든 뒤, 배열을 갱신하고, 목록을 렌더링한 다음, 데이터를 저장해 유지하는 영속성(persistence)을 시도합니다. 이후 수업에서는 실패 처리까지 명확히 다룹니다. 지금은 메모리에 있는 상태, 저장된 상태, 화면에 보이는 페이지를 구분하세요.

불변 조건(invariant)은 지원하는 어떤 동작을 수행한 뒤에도 참이어야 하는 규칙입니다. 이 프로젝트에서는 모든 책의 제목이 비어 있지 않아야 하고, `read` 필드는 불리언이어야 합니다. 식별자는 목록 안에서 중복되지 않아야 합니다. 이런 규칙은 개발자와 도우미 모두에게 "잘 작동하게 해 줘"보다 정확한 기준을 제공합니다.

구현을 요청하기 전에 설명부터 요청해 보세요.

```text
바닐라 JavaScript 독서 목록에 책 한 권을 추가할 때의 데이터 흐름을
설명해 줘. 메모리 내 상태, DOM 렌더링, localStorage를 구분해 줘.
아직 코드는 작성하지 말고, 실패할 수 있는 경우 두 가지를 짚어 줘.
```

답변은 작동 방식을 이해하기 위한 초안으로 받아들이세요. 낯선 브라우저 API는 문서와 대조해 확인하세요. 모델은 존재하지 않는 메서드(method)를 만들어 내거나, 경계 사례(edge case)를 놓치거나, 프로젝트에 필요 없는 의존성(dependency)을 제안할 수 있습니다.

## 실습: 작고 관찰 가능한 동작 약속 정하기

처음으로 사용할 수 있는 버전을 설명하는 문장 네 개를 작성하세요. 정상 동작 하나, 잘못된 입력 하나, 저장에 대한 기대 하나, 의도적으로 둔 제한 하나를 포함하세요. "완전히 안전하다"나 "어디서나 작동한다"처럼 구체적으로 확인할 수 없는 주장은 피하세요.

<details><summary>작성한 약속 확인하기</summary>

합리적인 약속은 다음과 같습니다. 비어 있지 않은 제목을 제출하면 화면에 책 한 권이 추가됩니다. 공백만 입력하면 책이 추가되지 않고 메시지가 표시됩니다. 저장에 성공한 목록은 같은 출처(origin)에서 새로고침해도 유지됩니다. 목록은 기기 간에 동기화되지 않습니다. 각 문장은 따로 확인할 수 있습니다. 또 나중에 답해야 할 질문도 드러납니다. 저장에 실패하면 인터페이스에 무엇을 표시해야 할까요? 저장이 항상 잘된다고 암묵적으로 가정하기보다 이 질문을 적어 두는 편이 유용합니다.

</details>
