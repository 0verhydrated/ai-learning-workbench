## 트리거는 작업 완료가 아니다

<strong>트리거</strong>는 작업을 요청하고, <strong>스케줄러</strong>는 요청할 시점을 결정하며, <strong>워커</strong>는 실제 작업을 수행합니다. 일정이 저장되었다는 사실은 설정이 있다는 뜻일 뿐입니다. 워커가 시작되었는지, 유효한 자료를 가져왔는지, 결과가 전달되었는지는 별도로 확인해야 합니다. 따라서 예약됨, 시작됨, 완료됨, 전달됨을 서로 다른 상태로 기록합니다.

예를 들어 주간 뉴스 도우미에는 일요일 트리거뿐 아니라 정상적인 실행 환경도 필요합니다. 노트북이 잠들어 있다면 예약을 저장해도 프로세서는 일하지 않습니다. Hermes 문서는 예약 작업이 새로운 에이전트 세션에서 실행된다고 설명합니다 [1]. 매번 처음 시작하는 워커라고 생각하고 저장소 경로, 출처 정책, 출력 형식, 마감 시각, 영속 체크포인트 위치를 전달하세요. 어제 나눈 대화가 실행 문맥에 그대로 남아 있다고 가정하면 안 됩니다.

## 다섯 필드를 순서대로 읽기

일반적인 5필드 cron 표현식은 다음 순서를 사용합니다 [2].

```text
분     시   일(날짜)     월    요일
0      8    *            *     0
```

`*`는 허용되는 모든 값을 의미하며, 여기서 `0`은 일요일입니다. 따라서 `0 8 * * 0`은 <strong>스케줄러가 사용하는 시간대에서</strong> 일요일 08:00을 뜻합니다. 표현식 안에는 시간대 정보가 없습니다. UTC 스케줄러에 붙여 넣고 한국 시각으로 해석되기를 기대하면 안 됩니다.

요구 사항이 `Asia/Seoul` 기준 일요일 08:00이라면, UTC로 동작하는 스케줄러에서는 `0 23 * * 6`을 사용합니다. UTC 토요일 23:00에 해당하므로 시간뿐 아니라 날짜와 요일이 바뀌는지도 확인해야 합니다. 다음 코드는 파이썬 표준 라이브러리만 사용하며 실제 예약을 만들지 않습니다.

```python
from datetime import datetime, timezone
from zoneinfo import ZoneInfo

local = datetime(2026, 11, 8, 8, 0, tzinfo=ZoneInfo("Asia/Seoul"))
utc = local.astimezone(timezone.utc)
assert local.strftime("%A") == "Sunday"
assert utc.isoformat() == "2026-11-07T23:00:00+00:00"
assert utc.strftime("%A") == "Saturday"
print(local.isoformat(), "=>", utc.isoformat())
```

서머타임을 사용하는 지역에서는 고정 UTC 표현식만으로 연중 같은 현지 시각을 유지하지 못할 수 있습니다. 지원된다면 지역 이름으로 시간대를 지정하고 시계가 바뀌는 시점 전후의 실행 예정 시각을 확인하세요. cron 구현에 따라 일요일 번호나 날짜 필드와 요일 필드를 함께 지정했을 때의 해석도 다릅니다. 문법을 보편적인 규칙으로 외우기보다 사용하는 스케줄러의 규칙을 확인해야 합니다.

## 일정과 이벤트 중 선택하기

<strong>폴링</strong>은 변화가 있는지 반복해서 묻는 방식이고, <strong>웹훅</strong>은 생산자가 변화를 감지했을 때 이벤트를 전달하는 방식입니다. 매주 발행하는 요약에는 일정이 자연스럽고, 풀 리퀘스트 리뷰에 반응하는 작업에는 이벤트가 자연스럽습니다. 웹훅에도 서명 검증, 재전송 공격 방지, 중복 처리가 필요합니다. 이벤트 기반이라는 이유로 정확히 한 번만 전달되는 것은 아닙니다.

GitHub Actions의 예약 워크플로는 기본 브랜치에서 실행되며 문서에는 지연 가능성도 명시되어 있습니다 [2]. 호스팅된 워크플로는 노트북의 전원 상태에 의존하지 않지만, 별도의 로컬 Hermes 게이트웨이까지 클라우드에서 실행해 주지는 않습니다. 각 워커가 실제로 어디에서 도는지 확인하세요.

## 활성화하기 전에 확인할 계약

실행 계약에는 적용 시간대, 다음 세 번의 예정 시각, 중복 실행 정책, 최대 실행 시간, 놓친 일정의 처리 방식, 성공 결과의 전달 위치를 적습니다. 지난주 작업을 건너뛸지 한 번 보충할지 결정하세요. 수개월치 발행 작업이 한꺼번에 재생되어서는 안 됩니다.

Hermes에서는 예약 옵션을 사용하기 전에 설치된 명령이나 도구 스키마를 최신 문서와 비교하세요. 문서와 설치 버전은 다를 수 있습니다. 저장된 다음 실행 시각과 활성화 상태를 확인하고, 명시적으로 허용된 드라이런을 수행합니다. 이 수업에서는 실제 예약을 생성하지 않습니다. 인증 정보는 실행 환경의 비밀 저장소에 두고 cron 문자열, 프롬프트, 커밋 파일, 알림 메시지에 넣지 마세요.

## 오해와 연습

“cron이 표현식을 받아들였으니 뉴스레터가 도착한다”는 말은 설정과 전달을 혼동합니다. 단계마다 별도의 증거가 필요하며 마지막에는 지정한 전달 위치를 다시 읽어 확인해야 합니다.

<strong>연습:</strong> UTC 워커에 `0 8 * * 0`이 설정되어 있는데 편집자는 한국 시각 일요일 08:00을 요청했습니다. 무엇을 고치고 무엇을 더 확인해야 할까요?
