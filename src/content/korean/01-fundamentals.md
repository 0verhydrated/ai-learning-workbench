## 직접 확인하고 책임질 일 정하기

<strong>바이브 코딩(vibe coding)</strong>은 흔히 원하는 결과를 설명하고, 생성된 변경 사항을 받아들인 뒤, 화면이 그럴듯한지 보고 성공 여부를 판단하는 방식을 말합니다. 한 번 쓰고 버릴 실험에는 유용할 수 있습니다. 하지만 무엇이 바뀌었는지 설명하지 못하거나, 오류를 재현하거나 누군가의 데이터를 복구할 수 없다면 위험해집니다. 화면이 멀쩡해 보여도 새로고침 한 번에 독서 목록이 사라질 수 있습니다.

<strong>책임 있는 AI 보조 개발</strong>에서도 빠른 피드백은 유용합니다. 다만 어떤 동작을 만들지 정하고, 변경 사항을 살펴보고, 검사를 실행해 배포해도 되는지 판단하는 일은 개발자의 몫입니다. 도우미에게 코드 제안이나 낯선 문법의 설명을 맡길 수는 있어도 제품에 관한 결정까지 넘겨서는 안 됩니다. <strong>확신에 찬 설명이 테스트 결과를 대신하지도 않습니다</strong>.

이 과정에서는 별도 프레임워크를 쓰지 않는 바닐라(vanilla) HTML, CSS, JavaScript로 독서 목록을 만듭니다. 책 제목을 추가하고 읽은 책을 표시하며, 브라우저의 로컬 저장소인 localStorage에 목록을 보관합니다. 같은 브라우저에서만 쓰는 목록으로 범위를 정하고, 계정이나 공유 목록, 서버 데이터베이스는 만들지 않습니다. 전체 동작을 따라갈 수 있도록 프로젝트를 작게 유지합니다.

## 브라우저의 역할 분담 이해하기

<strong>HTML은</strong> 폼(form), 입력란, 버튼, 목록처럼 의미와 구조를 표현합니다. <strong>CSS는</strong> 간격과 눈에 보이는 키보드 포커스(focus)를 비롯한 표시 방식을 제어합니다. <strong>JavaScript는</strong> 이벤트(event)를 처리하고, 애플리케이션 상태(state)를 바꾸고, 문서를 갱신합니다. <strong>문서 객체 모델(DOM, Document Object Model)</strong>은 브라우저가 이 문서를 객체로 표현한 것입니다.

버튼처럼 보인다고 클릭이나 키보드 조작이 되는 것은 아닙니다. 키보드로도 활성화할 수 있는 실제 `button` 요소를 우선 사용하세요. JavaScript 배열(array)에 넣은 제목 역시 저절로 화면에 나타나지 않습니다. 프로그램이 DOM에 반영해 화면에 표시하는 렌더링(rendering) 과정이 필요합니다. 배열도 영구히 남지 않습니다. 페이지를 새로고침하면 JavaScript가 처음부터 다시 실행됩니다.

```js
const books = [
  { id: 'book-1', title: 'A Wizard of Earthsea', read: false }
];

const unread = books.filter(book => !book.read);
console.log(unread.map(book => book.title));
```

이 배열에는 객체(object)가 들어 있습니다. 각 객체는 변하지 않는 식별자(identifier), 문자열(string)로 된 제목, 참과 거짓으로 읽기 상태를 나타내는 불리언(boolean) 값을 담습니다. 필터는 조건에 맞는 객체로 새 배열을 만들 뿐, 저장까지 하지는 않습니다. 브라우저 콘솔(console)에서 실행하기 전에 새 배열에 무엇이 들어갈지 예상해 보세요.

## 제목이 목록에 추가되는 과정 따라가기

사용자가 제목을 제출하면 먼저 폼 이벤트를 받습니다. 입력값의 앞뒤 공백을 제거하고 검증한 뒤 책 객체를 만들어 배열에 추가합니다. 그 배열로 목록을 렌더링하고, 데이터를 저장해 유지하는 영속성(persistence)을 확보하려고 시도합니다. 저장이 실패했을 때의 처리는 이후 수업에서 다룹니다. 지금은 <strong>메모리에 있는 상태</strong>, <strong>저장된 상태</strong>, 화면에 보이는 페이지가 서로 다를 수 있다는 점을 구분해 두세요.

<strong>불변 조건(invariant)</strong>은 프로그램이 지원하는 어떤 동작을 수행한 뒤에도 지켜져야 하는 규칙입니다. 이 프로젝트에서는 모든 책에 비어 있지 않은 제목이 있어야 하고, `read` 필드는 불리언이어야 합니다. 식별자도 목록 안에서 중복되면 안 됩니다. "잘 작동하게 해 줘"라고 요청하는 것보다 이런 규칙을 정해 두는 편이 개발자와 도우미 모두에게 명확한 기준이 됩니다.

구현을 요청하기 전에 설명부터 요청해 보세요.

```text
바닐라 JavaScript 독서 목록에 책 한 권을 추가할 때의 데이터 흐름을
설명해 줘. 메모리 내 상태, DOM 렌더링, localStorage를 구분해 줘.
아직 코드는 작성하지 말고, 실패할 수 있는 경우 두 가지를 짚어 줘.
```

답변은 작동 방식을 이해하기 위한 초안으로 받아들이세요. 낯선 브라우저 API는 문서와 대조해 확인하세요. 모델은 존재하지 않는 메서드(method)를 만들어 내거나, 경계 사례(edge case)를 놓치거나, 프로젝트에 필요 없는 의존성(dependency)을 제안할 수 있습니다.

## 실습: 직접 확인할 수 있는 동작 약속 정하기

첫 버전에서 어떤 동작을 기대하는지 문장 네 개로 적어 보세요. 정상 동작 하나, 잘못된 입력 하나, 저장에 대한 기대 하나, 의도적으로 둔 제한 하나를 담습니다. "완전히 안전하다"나 "어디서나 작동한다"처럼 구체적으로 확인할 수 없는 주장은 피하세요.

<details><summary>작성한 약속 확인하기</summary>

예를 들어 이렇게 약속할 수 있습니다. 비어 있지 않은 제목을 제출하면 화면에 책 한 권이 추가됩니다. 공백만 입력하면 책은 추가되지 않고 메시지가 표시됩니다. 저장에 성공한 목록은 같은 출처(origin)에서 새로고침해도 유지됩니다. 목록은 기기 간에 동기화되지 않습니다. 각각 따로 확인할 수 있는 문장들입니다. 저장에 실패했을 때 화면에 무엇을 표시할지는 아직 정하지 않았습니다. 항상 저장될 것이라고 가정하지 말고, 이후 저장 기능을 다룰 때 답할 질문으로 적어 두세요.

</details>
